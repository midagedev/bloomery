## 4. 수수께끼 해결 (코드 + 산수)

### (a) matmul_q Q4_K의 행바이트 ≈ 1,364 B — 두 텐서의 혼합 평균이다
측정: 148.05 MB/step ÷ 108,544 rows/step = **1,363.9 B/row**(n96:158; 53 calls × 2,048 rows, 호출마다 행수 동일). 코드상 단일 matmul_q Q4_K 호출은 블록당 1텐서(ops.rs:223)이므로, 53호출이 서로 다른 k의 텐서들일 수밖에 없다. 해(전부 산수로 닫힘):

- **27 calls = blk.N.attn_output**: k = 16 heads×v_head 128 = 2,048 → 8블록×144 = **1,152 B/row**. 27×2,048×1,152 = 63.70 MB.
- **26 calls = blk.N.ffn_down_shexp**(moe.rs:538-548의 shexp down): 잔여 84.35 MB ÷ (26×2,048 rows) = **1,583.9 B/row → k = 2,816 = 11×256** ✓ Q4_K 계약(256배수) 충족.
- 검산: (27×1,152 + 26×1,584)/53 = 1,363.9 B/row, 총 148.05 MB ✓. 즉 "k=2048이면 1,152 B여야 한다"는 전제가 틀렸고, 정답은 **k=2,816인 ffn_down_shexp가 끼어 있다**. 이 파일의 shexp 중간폭 = 2,816(공식 config 아님 — 이 재양자화 GGUF의 실측 치수; 아래 (c)·§5의 다른 교차검증들이 같은 값을 독립적으로 지지).

### (b) matmul_q F32, 26 calls/step × 64 rows, dequant CPU 298 ms — **MoE 라우터 게이트다**
코드 동일시: moe.rs:219 `let logits = matmul_q(gguf, gate_inp, x)?; // {n_expert, n_tokens}, F32 weights` — blk.N.ffn_gate_inp, 26 MoE 레이어 × 1 call. 산수: 64 rows × k 2,048 × 4 B = **8,192 B/row**, 26×64×8,192 = 13.63 MB/step = 표의 13.63(n96:163) ✓ 정확히 일치. "dequant" 스테이지(298.47 ms CPU합)는 F32 경로의 바이트 워크 자체다(ops.rs:311-314, f32 리틀엔디언 복사) — 13.63 MB를 3.11 ms CPU로 = 4.4 GB/s/코어합, DRAM 균등분 수준이라 느린 게 아니라 워크가 작아 패킹이 안 되는 것(활용도 21%).

(n8:95,197; n96:183,373) **디스패치 수는 두 실행이 스텝당 동일(322, 구조는 ctx-불변)** — 파킹만 스텝당 0.6→139.9(~224×) 늘었다. 풀은 스핀 20,000회(threads/src/lib.rs:7,30) 후 condvar로 잠든다: 파킹은 디스패치 수가 아니라 **대기 길이가 고정 스핀 예산을 넘는 빈도**의 함수다. 후보 설명(추정, 미측정): (i) N=96 실행이 길어(3.07 s vs 0.22 s) 부스트 클럭→정상 클럭으로 안정되며 직렬 구간이 실제로 늘어나고, 반복-카운트 고정 스핀은 상대적으로 짧아진다; (ii) 한번 잠긴 워커의 깨움 지연이 다음 디스패치 도착을 밀어 cascade. 레벨2에서 워커가 행마다 타이머 세금으로 느려지자 파킹이 절반(13,430→6,890)으로 떨어지는 것이 두 설명 모두와 양립한다(워커가 청크를 오래 물수록 파킹 감소). **비용 추정(유도, 가정: 완전-파킹 디스패치 경계 433회[13,430÷31] × 경계당 깨움 ~20–150 µs) = 런 총 9–65 ms ≈ 0.1–0.7 ms/step** — 파킹은 증상이지 원인이 아니고, 스텝 시간 차이는 §5-1대로 flash에서 온다.

## 6. 가설 검정

### H1. "달성 GB/s는 rows/call과 상관하고 커널 품질과 무관하다" — **방향은 확증, 변수 지정은 수정**
| 사이트 | rows/call | MB/디스패치 | 달성 GB/s | %STREAM | 코어당/커널 |
|---|---:|---:|---:|---:|---:|
| Q6_K lm_head | 102,400 | 172.0 | 119.3 | 80.8% | 22.3%(대역폭 벽) |
| Q5_1 blk.0 down | 2,048 | 16.81 | 75.4 | 51.0% | 15.7% |
| batch Q5_0 down | 12,288 | 11.90 | 67.8 | 45.9% | 16.0% |
| batch Q3_K(moe g/u) | 16,896 | 14.86 | 70.3(53-call 합) | 47.6% | 20.4% |
| batch Q3_K(wv_b) | 2,048 | 0.45 | (혼재) | | |
| Q3_K singles | 3,072/576/2,816/10,944 | 0.51–9.63 | 51.2 | 34.7% | 14.8% |
| Q4_K | 2,048 | 2.36/3.24 | 47.5 | 32.2% | 10.5% |
| q_nope2 | 8,192 | 1.11 | 22.9 | 15.5% | 스칼라 |
| F32 라우터 | 64 | 0.52 | 13.4 | 9.1% | – |

Q6_K(102,400 rows, 119 GB/s) ≫ Q4_K(2,048 rows, 47) — 지시된 대비는 성립. 그러나 **rows/call만으로는 반례 둘**: Q5_1과 Q4_K가 같은 2,048 rows/call인데 75 vs 47(Q5_1의 행이 8,208 B로 5–7배 길어 디스패치당 바이트가 16.8 vs 2.4–3.2 MB), q_nope2가 8,192 rows/call인데 23(커널이 스칼라). **실제 예측 변수는 "디스패치당 바이트"(상각 분모)이며, 커널 품질은 그 상단에서만 변별력이 있다** — 위 표에서 GB/s는 MB/디스패치의 단조 포화 함수(172→119, 16.8→75, 12–15→68-70, 2–10→47-51, 0.5–1.1→13-23)이고, 커널을 바꿔도 Q6_K(81% STREAM)는 더 못 올라간다. 판정: **부분 확증(수정)**.

### H2. "flash는 #1 사이트(18.8%)인데 KV 바이트가 작아 대역폭이 아니라 지연/SIMD 한계다" — **확증**
- #1 확인: 576.92/3,064.93 = 18.8%(n96:155).
- 바이트율: 평균 1.695 MB/6.010 ms = 0.28 GB/s; **ctx 101에서도** 27×102키×1,152 B = 3.173 MB ÷ (fit 0.1118×102 = 11.40 ms, 유도) = **0.278 GB/s — 모든 ctx에서 동일**(시간과 바이트가 모두 ∝ctx). 이는 STREAM의 0.2%, 4.6 GB/s×32스레드의 0.2%다.
- 반대편 근거: 행-키당 비용 0.1118 ms/432행-키 = 259 ns ≈ 스칼라 f32 FMA ~1,100개(kq 576 + V 512)의 사이클 비용과 정합. 코드는 원소별 `half_to_f32(k[·]).mul_add(q[·], …)`(attn.rs:844-858)과 키당 `v_expf` — SIMD/F16C가 전혀 없다. 대역폭이 아니라 **스칼라 연산/지연 벽**이다.

### H3. "swiglu 131 ms + 비내적 사이트 합계의 비중" — 수치화
swiglu 1.370 ms/step = 4.3%. 비내적 직렬 사이트 합(swiglu+wv_b self+moe_trace+moe_expert_io+f32_tensor+rms_norm+attn_params+moe_route+moe_setup+rope+residual+kvr+gain+latent+is_moe+embed+ffn_weights+head_params) = **3.303 ms/step = 10.3%**. 여기에 내적이지만 비-qdot인 flash 6.01 + q_nope2 1.31 + F32 라우터 1.02를 더하면 **11.65 ms = 스텝의 36.5%** — qdot 커널이 담당하는 내적(bagch Q3_K/Q5_0/Q3_K단일/Q4_K/Q6_K/Q5_1 합 19.60 ms = 61%)을 제외한 나머지가 3분의 1 이상이다.

### 스텝 분해(종합, 레벨2 세금보정 기반, 유도)
dot 연산의 완전-병렬 하한 220.9 ms CPU÷32 = **6.9 ms** ＋ flash 5.4 ＋ 직렬 quant 4.0 ＋ 사이트 내 오케스트레이션 잔여 ~10.2 ＋ 직렬 비내적 ~3.3 ＋ q_nope2 dot 0.35 ≈ **30.2 ms = 실측 레벨2 벽 30.19**(폐합 ✓). 즉 스텝의 ~2/3는 "연산 자체"가 아니라 flash의 스칼라 루프와 패킹 빈 자리다.
