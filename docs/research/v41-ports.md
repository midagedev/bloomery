2026-09-21. 원문은 [`v41-ports-report.md`](v41-ports-report.md)(영문, 위임 조사, 주장마다 `file:line`). 대상은 ik main
`3bb386eb` 위의 세 브랜치다: `mine`(우리 PR ikawrakow/ik_llama.cpp#2455), `skel`(Skelectric `v41-on-vision`),
`phyl`(Phylliida `v41-flash`, 닫힌 초안 #2449). `~/repo/upstream/v41-ports/`에 체크아웃돼 있다. 어느 것도 따라가지
않는다 — 각자가 값을 치르고 배운 것만 추린다. 수식의 출처는 여전히 [`v41-ops.md`](v41-ops.md)다.

## 세 트리 어디에도 없는 것

Phylliida의 "3090 한 장에서 6–8 tok/s"는 PR 본문의 말이고 트리에는 없다. 그 브랜치의 전문가 캐시 문서와 수치는 전부
GLM-5.3-Flash(288 전문가, top-8)에서 잰 것이고 V4.1로 돌렸다는 기록은 없다. 세 트리를 통틀어 V4.1 종단 tok/s는
우리 자신의 engram 선행 읽기 커밋 하나뿐이다: 토큰당 major fault 41–62 → 1–11, 13.6 → 18.4 tok/s, 행이 이미 캐시돼
있으면 18.8–19.0.

## engram

셋 다 호스트에서 해시하고 mmap의 페이지 캐시에 기댄다. `pread`·`io_uring`·`O_DIRECT`·뜨거운 행 캐시는 아무도 안 쓴다.
`mine`은 행마다 `posix_madvise(WILLNEED)`를 디코드 호출 안에서 걸고, `skel`은 **모든 행 id를 먼저 해시한 뒤** 한꺼번에
건다(해시하는 동안 아무것도 폴트하지 않게), `phyl`은 선행 읽기가 없다. 우리 계획(샘플링 직후에 다음 토큰의 48행을
건다 — 한 스텝 전체가 여유)은 셋보다 이르다. 위 수치가 말하는 것은 이 규모에서 **폴트 수가 디코드의 병목**이라는
것이므로 engram 크레이트의 텔레메트리에 major fault 수를 넣는다.

해시 상수는 파일에서 읽는다. `skel`은 사이드카 파일에 두었고 없으면 경고만 하고 engram을 끈다 — 조용한 품질 저하다.
이력(앞 3토큰)은 **KV 셀에서 유도한다**(`mine`의 방식). `skel`의 3칸 꼬리는 기각된 draft 토큰으로 전진한 뒤 되돌리는
코드가 트리에 없고, `phyl`의 위치별 벡터는 서버의 빈 `seq_rm`에 지워져 둘째 턴에서 죽었다. 롤백의 소유자는 하나여야
한다. `skel`·`phyl`은 디퀀트한 F32 행(토큰당 49 KiB)을 올린다; 우리는 Q8_0 행 13 KiB를 그대로 올려 디바이스에서 풀 수
있다(아무 포트도 안 하는 것).

## 전문가 캐시(`phyl`, GLM에서 잰 것 — 모양만 가져온다)

캐시 단위는 한 층의 한 전문가(up+gate+down), 자리는 VRAM의 층별 슬롯 텐서이고 마지막 슬롯은 **쓰레기 슬롯**이다
(음수 id를 검사하지 않는 커널에 −1을 주지 않으려고). 히트·미스 두 경로를 항상 다 짓고 마스크는 모양이 아니라 **값**
이다 — 슬롯마다 정확히 한쪽만 0이 아니라서 단일 경로와 비트 동일하고, 분류를 디바이스 커널로 옮겨 그래프 캡처가
유지된다(캡처가 깨지면 TG −13.8 %를 잰 기록). 미스는 아무것도 복사하지 않는다(CPU가 호스트의 원본으로 계산) —
승격은 언제나 추가 트래픽이다. 입장은 **64스텝 창 안의 두 번째 미스**에서(승격 160 → 113/스텝), 속도 제한은 토큰
버킷, 프리필 중에는 읽기 전용. 값비싼 교훈 하나: 페이지 가능 메모리에서의 승격 복사는 드라이버 스테이징 락에서 임계
경로의 입력 복사와 직렬화돼 스텝당 ~27 ms를 도로 가져갔다 — **승격 스테이징은 고정(pinned) 메모리여야 한다**.
PCIe 실측: 고정 HtoD 26.2 GB/s(계산 스트림이 포화여도 26.15), 페이지 가능 14.4. 히트율 0.46–0.52에서
TG ≈ 9.01/(1−hit) 모델이 맞았다. V4.1은 384 중 6이고 전문가 조각이 더 작다 — 상수는 다시 재야 한다.

## 희소 어텐션, KV, 하이퍼커넥션

디코드에서 셋 다 마스크가 아니라 **고른 행을 모은다**(640행 목표가 맞다). 비율 2의 "두 토큰에 한 번 그룹 완성"은
그래프 분기가 아니라 스텝마다 호스트가 계산하는 **색인 계획**으로 푼다 — 그래프 모양이 일정해진다. 2단계 후보 블록은
`skel`만 구현했고 압축 위치 16,384 미만에서는 스스로 사라진다 — 미룬다. 인덱서의 Hadamard 회전은 V4 유물이다
(`skel`·`phyl`은 주석과 함께 껐고 `mine`은 q·k 양쪽에 남아 있다 — 점수는 보존되지만 순수 비용).

참조의 양자화 캐시를 구현한 것은 `skel`뿐이다: fp8-B32-E8M0(윈도우), fp4-B16-E4M3(압축 KV), fp4-B32-E8M0(인덱서 k·q),
스케일 바닥·RNE 반올림·니블 순서까지 참조와 바이트 비교가 되게 적어 두었다(`ggml-kv-quants.h:7-33` — 구현이 아니라
**명세로** 가져올 가치). 측정된 사실 하나: 인덱서 K만 양자화하고 Q를 같은 격자로 안 굴리면 top-k 선택이 **토큰의
100 %, 슬롯의 7.33 %**에서 바뀐다. 인덱서 키를 압축 저장한다면 Q도 같은 격자를 거쳐야 하고, 안 그러면 우리의
"인덱서 top-k id 정수 일치" 게이트가 결함이 아닌 이유로 깨진다.

하이퍼커넥션은 셋 다 ik의 융합 op 하나(`ggml_hc_pre`: 믹스 투영 + 시그모이드 + Sinkhorn 20회, CUDA 커널 있음)를
그대로 쓴다. 우리가 계획한 커널 단위(24차 gemv + Sinkhorn 4×4 한 런치)가 맞다.

## 출력이 달라지는 자리

MoE 가중치 합의 엡실론: 참조는 `Σ + 1e-20`. `skel`은 "게이트 행의 합이 0인 토큰"을 실제로 만나 고쳤고(`a59a2507`),
**`mine`(#2455)과 `phyl`은 엡실론 없이 나눈다** — 리드가 원본에서 확인했다(`llama-build-context.cpp:1547-1562`의
분기에 `DEEPSEEK41`이 없다; 1e-20 분기는 BAILINGMOE2/3·STEP35뿐). 앞선 보고서의 "포트가 6.1e-5로 클램프한다"는
LAGUNA 분기를 잘못 읽은 것이었다. 우리 엔진에는 처음부터 `Σ + 1e-20`을 넣고 합 0인 경우를 단위 테스트로 둔다.
engram 게이트의 `dot == 0`은 세 포트 모두 0.5(참조는 0.50025) — 무해. 범위 밖 engram 행은 `phyl`만 0으로 가린다.

## draft

`mine`에는 없다(#2455가 밝힌 대로 둘째 PR). `skel`은 DSpark를 별도 아키텍처로 돌린다. 기각 때 되돌릴 상태는 압축기
상태 링 + 윈도우 링(+ 이력을 따로 들고 있다면 engram 이력). `skel`이 밟은 두 함정은 우리 게이트 계획에 넣는다:
무관한 업스트림 리팩터 뒤 V4.1에서 체크포인트 경로가 조용히 죽어 있었고(`llama_model_has_recurrent`가 `DEEPSEEK41`을
몰랐다), 윈도우 자르기 버그는 배치 1에서는 깨끗한데 **여러 토큰 검증 배치**에서만 그럴듯하게 섞인 텍스트를 냈다
("MK-8823"은 문서에 없는 코드). 추측 디코딩 게이트는 깊은 되감기 뒤의 다토큰 검증 배치를 반드시 돌린다.

## 계획에 넣는 것

1. engram 크레이트(B3): 해시를 전부 먼저, 표는 그다음; 선행 읽기는 샘플링 직후; 이력은 KV에서 유도; major fault 계수.
2. MoE 정규화 `Σ + 1e-20` + 합 0 단위 테스트(V4.1 MoE 커널을 쓸 때).
3. 전문가 배치(B1·B2)에 두 경로 값-마스크 + 쓰레기 슬롯 + 둘째 미스 입장 + 고정 스테이징을 설계 입력으로.
4. 압축 비율 기계는 호스트 색인 계획으로(그래프 분기 없음).
5. KV 양자화는 뒤로 미루되, 할 때는 `skel`의 규칙 표를 명세로 쓰고 인덱서 Q를 같은 격자로.
6. 추측 디코딩 게이트에 다토큰 검증 배치.
7. 안 하는 것: Hadamard, 사이드카 상수, 2단계 후보 블록(16k 위치 전까지).
