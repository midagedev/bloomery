# CPU 오프로딩에서 두 프로세서를 같이 돌리기 — 엔진들이 실제로 하는 것

2026-09-21. 엔진 소스 독해 조사(opus 서브에이전트), 원문은 [`hybrid-engines-report.md`](hybrid-engines-report.md). 학술 문헌과 형식 모델은 별도 조사(`hybrid-lit`)가 하고 있고, 둘을 맞댄 종합은 그 뒤에 `hybrid.md`로 쓴다. ik 인용은 리드가 로컬 체크아웃에서 줄까지 확인했다(`ggml-backend.cpp` 940·2019·2083·2221·2254·2398·2483행, `GGML_CUDA_MIN_BATCH_OFFLOAD` 32). 시간은 전부 **유도값**이고 GPU 대역폭을 두 눈금으로 괄호 친다: 700 GB/s(커널 바닥 — 우리 엔진이 볼 쪽)와 247 GB/s(오늘의 ik 전체 패스 평균, 정지 포함).

## 리드의 스펙 오류 하나

스펙에 "호스트 전문가는 층·토큰당 약 0.20 ms"를 V4.1의 사실처럼 적었다. 그 수치는 09-17에 **Qwen3.6-35B-A3B Q6_K, A6000**에서 잰 것이다(조사는 V2-Lite로 추정했는데 그것도 아니다). V4.1은 전문가 하나 16.77 MB × 6 = 101.1 MB ÷ 147.7 GB/s = **0.684 ms/층**(유도)이고 조사의 산술은 전부 이 값을 쓴다.

## 직렬 대기는 사실이고, 비용은 동기화가 아니라 직렬화다

ggml 스케줄러는 분할을 평범한 `for`로 돌고, CPU 백엔드의 `graph_compute`는 스케줄러 스레드를 막으며(`.synchronize = NULL`), 경계마다 `ggml_backend_synchronize`를 부른다(라우터 ids 읽기 포함). ik의 병렬 실행기는 `n_backends > 2 && split_mode_graph && has_reduce`(다중 GPU all-reduce)일 때만 켜지고, 그 안의 OpenMP 팔은 CPU 백엔드가 분할을 둘 이상 가지면 물러난다. mainline에는 병렬 실행기가 아예 없다.

그런데 경계 비용은 토큰의 약 1%다(80회 × 약 7 µs). 버려지는 것은 직렬화 자체다: 실측 56.5 ms 토큰 = 호스트 전문가 22.6 + GPU 쪽 33.9이므로 **GPU는 토큰의 40%, CPU는 60%를 논다**(유도). 경계만 싸게 만드는 라운드는 최대 2%를 되찾는다.

## 돈이 되는 것 (전부 출력 불변)

| | 무엇 | 이득, 배치 1 (700 … 247 GB/s) |
|---|---|---|
| R1 | 라우터 직후 호스트 전문가를 띄우고 **공유 전문가(+GPU에 캐시된 전문가)를 동시에** 돌려 `moe_combine`에서 합류 | −5.6 … −10.4% |
| R3 | VRAM 전문가 캐시(v41-ports의 설계 그대로), 적중률 0.5 가정 | −27.8 … −9.3% |
| R1+R3 | | **−41 … −33%** |
| R2 | CPU 경계를 캡처된 층 그래프 **안에** 넣기 | 직접은 −0.7 … −2.1%, 그러나 R1이 그래프 재생을 잃지 않게 하는 조건 — 캡처를 잃으면 ik −10.6%(우리 실측), Phylliida −13.8% |

V4.1의 공유 전문가는 층당 37.6 MB(q8_0) = 라우팅 전문가 2.24개 분량이다. 문헌의 모델들보다 R1이 더 값진 이유다.

이것을 실제로 하는 시스템은 KTransformers 하나다(소스 독해): CPU 전문가를 제출하고 → GPU에서 공유 전문가를 돌리고 → 합류하는데, 그 둘이 **캡처된 CUDA 그래프 안의 `cudaLaunchHostFunc` 호스트 노드 둘**이고 버퍼는 전부 pinned다. "CPU 연산이 들어간 단일 그래프" 주장은 확인됐다. HybriMoE(A6000 + 10코어로 묶은 Xeon, KTransformers 대비 1.70× — 10코어라 CPU 다리가 인위적으로 길다, 수치는 옮겨 오지 않는다)가 그것을 캐시된 라우팅 전문가까지 일반화했다.

**캐시에는 가장 싼 정답 크기가 있다.** R1이 들어가면 층 벽시계는 `나머지 + 경계 + max(호스트 잔여, 공유 + GPU 전문가)`라서, GPU 쪽이 긴 막대가 되는 순간 승격은 더 사지 못한다 — 247 눈금에서는 적중률 약 0.5, 700 눈금에서는 약 0.83. 어느 눈금에 있는지는 우리 gemv 효율이 정하므로 커널 작업이 캐시 크기 결정의 입력이다. V4.1(384/top-6)의 적중률은 어디에도 측정이 없다 — Phylliida의 0.46–0.52는 GLM-5.3-Flash(288/top-8)의 것이고 V4.1은 전문가당 기저율이 더 낮다. **라우터 id 추적을 재생해 세는 실험은 GPU가 필요 없고 지금 할 수 있다.**

## 돈이 안 되는 것과 그것을 죽이는 숫자

- **전문가를 PCIe로 올려 GPU에서 계산**: 같은 바이트가 어느 쪽으로든 움직이는데 호스트 길이 5.6배 넓다(147.7 대 26.2 GB/s). 전문가 **하나**를 올리는 값(0.640 ms)이 여섯을 전부 호스트에서 계산하는 값(0.684 ms)과 같다. ik 자신의 규칙으로도 384/6에서는 배치 2048 이상이어야 한다. 올리는 것이 맞는 경우는 미래 토큰에 나눠 갚을 때뿐이고(7.14회 적중에 본전, 기저율이면 약 457토큰) 그것이 곧 캐시다 — 그래서 입장 규칙이 미스가 아니라 뜨거움의 증거여야 한다.
- **전문가 예측·프리페치**: 느린 저장소에서 GPU로 가중치를 미리 옮기는 기법들이다. 우리 가중치는 이미 DDR4에 있고 호스트가 제자리에서 계산한다 — 미리 가져올 것이 없다. 남는 쓸모는 "무엇을 승격할까"의 입력.
- **검증 배치 토큰을 전문가별로 묶기**: k=8에서 기대 고유 전문가 45.6개, 전문가당 1.05토큰. 묶을 것이 없고 ggml은 이미 묶는다. 우리 WKS-36 실측과 같은 말이다(라우팅 몫은 전혀 상각되지 않는다).
- **stale 잔차 선계산·적응 top-k·재학습 게이트**: 출력이 바뀐다.
- **AMX 기반 수치**: 전문가당 1.05토큰의 디코드는 스트리밍 읽기다. 우리는 대역폭 바운드다(14스레드에서 버스가 찬다).
- **engram에 GPUDirect Storage**: 대역폭이 아니라 I/O 횟수 문제(토큰당 48회 × 272 B).

**추측 디코딩이 순위를 뒤집는다.** k=8 검증 배치에서 호스트 다리는 5.2 ms/층으로 자라고 GPU 다리는 거의 그대로라, R1의 이득은 1.0–2.5%로 줄고 R3의 이득이 커진다.

## 합류 수단 — B2 라운드의 첫 확인

1순위는 host-mapped pinned 메모리 위의 스트림 메모리 연산(`cuStreamWriteValue32`로 넘기고 `cuStreamWaitValue32`로 합류, 그래프 노드는 `cuGraphAddBatchMemOpNode`)이고, 2순위가 KTransformers의 `cudaLaunchHostFunc` 호스트 노드다. **확인 안 된 전제 둘**: 박스 드라이버의 `CU_DEVICE_ATTRIBUTE_CAN_USE_STREAM_MEM_OPS`, cuda-oxide의 bindgen 산출물에 그 셋이 있는지. 두 수단의 지연도 잰 적이 없다 — 같은 프로브 하나로 잰다. 순서: 경계 버퍼(R4) → R2 → R1 → R3, 적중률 측정은 처음부터 병행.

## 읽기 패스가 필요한 단서 하나

`v41-ops.md`는 V4.1의 하이퍼커넥션 혼합이 **한 서브층 늦게 소비된다**고 적고 있다. 그것이 참조 `model.py`에서 문자 그대로 사실이면 다음 서브층 입력의 일부는 이번 서브층의 출력에 의존하지 않고, 호스트 전문가가 돌아오기 전에 다음 GPU 작업의 한 조각을 **정확하게** 시작할 수 있다 — 하이퍼커넥션을 가진 배포 모델이 없어서 문헌에 없는 겹침이다. 조사도 확인하지 않았다. 층간 겹침을 "불가능"으로 닫기 전에 `model.py`를 한 번 읽는다.

## 범위 밖에서 나온 것의 처분

`roofline.md`의 묵은 줄 둘(V4.1을 MLA라 부름; engram을 상주시켜도 처리량이 안 바뀐다 — 13.6 → 18.4 tok/s 실측과 모순)은 지금 고친다. plan·orchestration의 B2 카드 게이트에 GPU 유휴 비율과 합류 수단 결정을 넣는다(왕복 µs만 재면 틀린 축을 최적화한다) — 지금. 서빙 배치표를 캐시의 함수로 다시 쓰는 것은 B1. ik `ggml-backend.cpp:2398`의 핫 루프 `printf`와 `:2019`의 `k_set_sync = false`는 업스트림 후보로 rig-log 표에 적는다(둘 다 리드가 줄을 확인했고, 재현은 아직 없다).
