# GPU 전용 가중치 포맷 — 포맷을 바꾸면 배치 1 디코드가 어디서 빨라지는가

질문(사용자, 2026-09-21): "ExLlama처럼 별개의 모델 포맷을 쓰면 성능을 확 높일 지점이 있을까." 조사 라운드 둘(agy, gemini-3.8-flash-high)을 돌렸고, 리드가 핵심 주장을 클론된 원본에서 대조했다. 표시: **[확인]** = 리드가 소스에서 직접 읽음, **[보고]** = 조사 보고의 주장이고 리드 미확인, **[유도]** = 계산. 조사 원문은 세션 스크래치에 있고 리포에는 이 요약만 둔다.

## A. ExLlamaV2(EXL2) · ExLlamaV3(EXL3) — 코드에서 읽은 것

소스는 타르볼로 받아져 커밋 해시를 git으로 확인할 수 없다(보고는 해시를 적었으나 미확인). 파일은 2026-09-21에 받은 master다.

**EXL3의 MoE는 층당 런치 두 번이다 [확인].** `exllamav3_ext/quant/exl3_moe_coop_kernel.cuh` 머리 주석이 설계를 그대로 적는다: 커널 A = (전문가 런, 32열 그룹, 투영)마다 블록 하나로 gate·up을 같이 돌고, 128열 청크를 덮는 마지막 도착 블록이 **완료 카운터**를 보고 출력 회전·활성화·down 입력 회전까지 끝낸다. 커널 B = down, 마지막 도착이 슬롯들을 고정 순서로 합치고 공유 전문가를 병합해 저장한다. 호스트 개입이 없고, 전문가 가중치는 디바이스의 포인터 표(`*_ptrs_trellis`)로 찌른다. 런치는 `cudaLaunchCooperativeKernel`(그리드를 동시 상주 가능한 블록 수로 제한, `cudaOccupancyMaxActiveBlocksPerMultiprocessor`)이다. 같은 파일의 메모: MoE 디코드에서 k-분할은 "measured ineffective"라 1로 둔다. **이것은 포맷이 아니라 엔진의 성질이다** — 어떤 가중치 표현으로도 만들 수 있다. 우리 설계서의 결정 5("첫 판은 6전문가를 런치 6번")의 도착점이 이미 구현돼 있는 선례다.

**EXL3의 코드북은 표가 아니라 계산이다 [확인].** `codebook.cuh`의 `mul1`(cb 2): 트렐리스 인덱스에 상수 `0x83DCD12D`를 곱하고 `dp4a(x, 0x01010101, 0x6400)`로 네 바이트를 더한 뒤 fp16 FMA 한 번으로 스케일·바이어스를 건다. 룩업 테이블 0바이트. 같은 파일에 sm_86 전용 인라인 asm 훅과 "CUDA 13.2부터는 평범한 곱이 ~4% 빠르다"는 주석이 있다 — 저자가 3090을 1급 대상으로 조율한다는 뜻이다.

**int8 활성값 경로가 있다 [확인].** `exl3_gemv_int8_kernel.cuh`: `mul1` 코드북 값이 (x·M의 네 바이트 합)에 대해 아핀이므로, 활성값을 int8로 양자화하면 `dp4a(x·M, splat(a_int8), acc)` 한 명령이 "코드북(x) × a"를 낸다. 가중치를 부동소수로 풀지 않는다. 잔차 모드(두 번째 dp4a로 반올림 오차 r = a − q·i를 누적)는 활성값 유효 정밀도 15–16비트를 주장한다. 우리 q8_1 설계(정수 내적 + 블록 스케일)와 같은 계열이고, 스케일 평면이 아예 없다는 점이 다르다.

**EXL3의 바이트 [보고, 구조는 파일 목록과 일치].** 16×16 타일, 정수 비트레이트 K에서 타일당 정확히 256·K비트(패딩 0), 스케일 텐서 없음(부호 벡터 su·sv와 128점 Hadamard로 비간섭화; 변환은 GEMV 커널의 프롤로그·에필로그에 융합). K-quant는 스케일에 0.4–0.5 bpw를 쓴다. 제약: 두 차원이 128의 배수.

**EXL2 [보고].** 열 방향 32비트 워드 패킹, 그룹별 4비트 비선형 스케일((q+1)²·max), 한 텐서 안의 혼합 비트폭, 로드 시 비트 셔플로 fp16 가수에 맞춘 한 명령 디퀀트, act-order 순열은 로드 시 앞 층의 출력 열을 재배열해 런타임 게더를 없앤다(gate/up → down). MoE는 전문가마다 런치(16개 이하) 또는 호스트 동기 후 활성 전문가만 — V3에서 버린 설계다.

**공개 속도 [확인: exllamav2 README].** 3090Ti에서 Llama2-7B EXL2 3.0 bpw 217 t/s, 4.0 bpw 185, 5.0 bpw 164; TinyLlama 1.1B 3.0 bpw 656. 7B × 3 bpw ≈ 2.6 GB이니 대역폭 천장 ≈ 385 t/s의 **56%**[유도]다. 같은 눈금에서 ik는 이 카드의 V2-Lite에서 천장의 31%다 — 다만 dense 7B와 MoE 16B는 같은 문제가 아니다(MoE는 노드가 많고 커널이 작다).

**품질 [보고, 미확인].** 보고의 표는 QTIP 논문 수치와 GGUF K-quant 수치를 한 표에 섞었고 출처가 열마다 다르다. 주장의 골자 — 트렐리스 3.0 bpw ≈ Q3_K_M(3.44 bpw) 품질, 2 bpw대에서 격차가 더 큼 — 는 조사 B의 1차 출처 대조를 기다린다. **이 모델(V2-Lite, MoE)에서의 수치는 없다.**

보고에서 버린 것: Hadamard 비용을 FLOPs ÷ TFLOPS로 나눈 ns 산수(런치·동기 비용을 무시한 값), "100% 확신" 류의 수사, 우리 측정치(작은 커널 2.3 µs)를 "런치 오버헤드"로 옮겨 쓴 대목.

## 포맷 수준과 엔진 수준을 가른다

| 이득의 출처 | 수준 | 우리에게 |
|---|---|---|
| MoE 층당 런치 2번(완료 카운터, 디바이스 포인터 표) | 엔진 | GGUF 그대로 가능. P0b 스파이크와 결정 5의 직접 선례 |
| gate·up 한 커널, QKV 한 커널(입력 변환 1회) | 엔진 + 약한 포맷 제약(같은 비트레이트·같은 타일) | GGUF에서 gate·up은 같은 타입이라 이미 충족 |
| 스레드가 정렬된 워드를 연속으로 읽는 배치 | 로드 시 재포장 | 결정 4가 이미 허용 — 파일 포맷을 안 바꿔도 된다 |
| 스케일 평면 제거(0.4–0.5 bpw), 같은 품질에서 더 낮은 bpw | **포맷(양자화 방식)** | 읽는 바이트가 1차 항이므로 유일하게 천장 자체를 올린다. 대가: 오프라인 변환(헤시안 캘리브레이션), ik 오라클과의 결별 |
| 계산형 코드북 × int8 dp4a | 포맷 | sm_86에 맞는 형태. 트렐리스를 택할 때 같이 온다 |

**잠정 결론.** "포맷을 바꿔 확 빨라지는 지점"은 하나다: 같은 품질에서 비트를 줄이는 것. 3.44 → 3.0 bpw면 읽는 바이트 −13%, 2.5 bpw까지 품질이 버티면 −27%[유도]. 나머지 ExLlama의 속도는 대부분 엔진(런치 수, 융합, 메모리 배치)이고 GGUF 입력을 유지한 채 로드 시 재포장으로 얻을 수 있다. 그리고 포맷 전환에는 이 프로젝트 고유의 비용이 있다 — 정확성 기준이 ik의 출력(같은 GGUF, 같은 양자화)이라, 양자화를 바꾸는 순간 오라클이 "같은 수치"에서 "같은 품질(perplexity/KL)"로 바뀐다. 그러므로 순서는: ① 엔진 수준의 것을 GGUF 위에서 먼저 닫고(천장의 31% → EXL2가 보인 56% 급이 그 몫의 눈금), ② 그 뒤 남은 거리가 바이트 바닥이면 트렐리스 계열을 V4.1 단계의 선택지로 연다 — 호스트로 넘치는 모델에서는 bpw가 곧 PCIe·호스트 대역폭이라 값이 더 크다.
