# Jev 계열 분류기 — 드래프트 게이트와 전문가 재배치에 끼울 자리가 있는가

2026-09-24. opus 조사(원문 [`jev-placement-report.md`](jev-placement-report.md)), 09-21의 [`jev-routing.md`](jev-routing.md)의 후속. 사용자 질문: "오픈소스 구현이 많으니 투기(드래프트)와 전문가 재배치에 끼워 쓸 수 없나." 리드가 원본에서 확인한 것: Shalimov04/open-jev README(mmBERT-small 140M, Qwen 3.8-27B 교사, GPU p50 5.3–7.1 ms), SpecDec++(arXiv 2405.19715, 수락 예측 헤드, +7.2/9.4/11.1 %), Cascade(arXiv 2506.20675, MoE에서 투기가 1.5× 느려질 수 있고 5 %로 제한, 정적 K 대비 +7–14 %). 나머지 인용은 보고만 읽었다.

## 오픈소스 구현 (전부 저자 자기 보고 지연)

| 구현 | 모델 | 결정당 지연 |
|---|---|---|
| open-jev | mmBERT-small 140M(증류) | 5.3–7.1 ms(GPU) |
| von | ModernBERT-Large 395M | ~18 ms(GPU), 정확도 72 % 대 Jev 96.6 % |
| Verdict-open-jev | ModernBERT-base 151M + GLiClass, ONNX | p50 35.6 ms(CPU 1스레드) |
| open-jev-deberta-v3-large | 0.4B | 28 ms/10문항(H100) |
| openjev 27B, razorback/openjev 26B-A4B | 26–27B | 27–210 ms |
| JEV-CPU(Qwen3-0.6B) | 0.6B | ~1 s |

5 ms 아래는 없다. 토큰마다(스텝 35–40 ms) 부르기엔 가장 빠른 것도 13–15 %를 먹고, 카드 상주 26–27B는 VRAM(A6000 여유 ~1.3 GB)에 안 들어간다. awesome-jev 832개 프로젝트 목록(요약기가 읽음)에 투기·드래프트·MoE 배치·KV 항목은 없었다.

## (b) 전문가 재배치 — 결론: 분류기 없이 프리필 통계로

- 우리 슬롯 맵은 디바이스 표다(`chain/ffn.rs:509` `slots: &DeviceTensor<u32>`). 층별 개수를 지키는 교체는 표 쓰기 + expert 업로드이고 그래프 재캡처가 없다(호스트 티어 사본의 라이브 교체와 층별 개수 의존 grid는 미확인).
- 분류기가 주는 것은 "코드/한국어/산문/스레드" 라벨 → 코퍼스 평균 목록이고, 상한은 in-domain 목록의 적중 57.6–73.5 %(혼합 정적 40.1–48.9 %, rig-log 09-23)다. 프리필의 라우터 통계는 **이 요청**의 실제 선택이라 라벨보다 엄격히 구체적이고 비용 0이다. 선행 연구(DAOP: 프리필 활성으로 층당 절반을 CPU↔GPU 교체, A6000, 최대 +8.2 %; fMoE: 힌트는 MoE 자기 임베딩)도 외부 모델이 아니라 모델 자신의 신호를 쓴다.
- 산수[유도]: H2D 26.2 GB/s(`v41-ports.md:38`), expert 16.77 MB → 0.64 ms/개, 층당 4개 교체 97 ms, 8개 195 ms, 888슬롯 전부 568 ms. 이득 상한은 +10–33 pp × 0.30 ms/pp = 3.0–9.9 ms/스텝(E11이 예측 7–10에 −4.5로 왔으니 상한으로 읽는다). 200토큰 프롬프트도 프리필이 초 단위라 업로드는 복사 스트림에 숨고, 최악 189토큰 안에 회수된다. 미유도 항 하나: 디코드와 겹치는 H2D는 호스트 DRAM을 같이 읽어 호스트 티어를 늦춘다.
- 프리필 전 결정이 값을 하는 조건은 셋(목록이 라우팅을 보기 전에 상주해야 함; 프롬프트가 너무 짧음; 첫 토큰 시간이 교체를 못 삼킴)인데 배치 1 단일 스트림·토큰별 프리필인 우리에겐 하나도 해당 없다. 짧은 프롬프트는 정적 목록에서 출발해 생성 토큰으로 갱신하면 된다.

## (a) 드래프트 게이트 — 결론: 모델이 아니라 공짜 특징으로

- 논문들(SpecDec++·DISCO·Cascade)이 헤드를 학습하는 이유는 드래프트가 logits를 가진 모델이기 때문이다. 우리 lookup 드래프트는 **n-gram 일치 길이와 출현 횟수**를 공짜로 갖고, E5에서 이기는 몫은 n=3 실제 반복이었다. Cascade의 규칙(효용 = 토큰 이득 ÷ 검증 비용 < 1이면 중단)은 옮겨 쓸 만하다.
- Jev 모양의 자리는 요청 단위 드래프터 선택(lookup 대 DSpark, E5: 코드 0.595 대 한국어 0.288)뿐인데, 한글 비율 규칙이나 이동 평균 수락률이 같은 일을 모델 없이 한다.

## 실험 (플랜 E19·E17에 등록)

- **E19(먼저, 오프라인 수 분)**: `draft-accept.py`를 네 코퍼스 + 엔진 greedy 출력(E5b)에서 확장해 일치 길이 n=1/2/3/≥4·출현 횟수별 수락률을 재고, 정책 넷(항상 쌍, n≥k만 쌍, 로지스틱 게이트, 오라클)을 처리량 Σ(1+수락)/Σ(쌍이면 r, 아니면 1)로 r=1.21·1.29에서 채점. 오라클이 항상-쌍보다 2 % 미만 앞서면 게이트 버림; n≥k 규칙이 오라클 1점 안이면 규칙 채택 후 같은 임대 A/B. 한국어(0.288 대 손익분기 0.21–0.29)가 경계.
- **E17에 열 추가**: 문서 앞 N=64/256/1024 토큰의 라우터 선택으로 층별 순위를 만들어 나머지의 바이트 가중 적중을 재고, 혼합 정적(40.1–48.9)·in-domain(57.6–73.5, 완벽한 분류기의 대리)과 비교. N=256 접두가 in-domain에 닿으면 분류기 없이 E18(프리필 통계) 개방; 정적 근처면 E18 폐기; in-domain이 작은 N에서 접두를 5 pp 넘게 이길 때만 분류기(그때도 규칙 먼저, 인코더는 규칙이 지면).

버리는 것: 디코드 루프 안의 외부 분류기, 호스티드 Jev API, 카드 상주 26–27B 변형. simple-jev의 logit 읽기는 09-21대로 값싼 사후 평가기로만.
