# q3fstep 보고 (GQA 프리필 flash의 스텝 모양, 스위즐, 프롤로그 설계, 2026-09-26)

> 리드 메모(2026-09-26). 아래는 설계 라운드 `q3fstep`(opus)의 보고 원문과, 시팅 16 뒤에 받은 추가분이다. 코드와 빌드는 없다.
> 처음 과제는 FA2의 스텝 모양(배리어 뒤에 softmax)을 우리 `gqa_prefill_flash`로 옮기는 설계였는데, 시팅 16이 판을 바꿨다.
> 우리 커널은 K/V를 L2→SM 섹터로 1.5배 읽었다(102,959,116, 바이트 하한 69,339,136). 원인은 272 B 패딩 행이다. 홀수 키 행의
> cp.async가 32 B 원본 섹터 하나마다 섹터 둘을 센다. 보고는 순위를 ① 16 B 청크를 `row & 7`로 XOR 스위즐한 256 B 행 ② 프롤로그
> 다이어트 ③ fstep으로 바꿨다. 기제는 시팅 17의 패딩 탐침으로 확정했다(288 B 행은 바이트 하한을 읽는다). ①과 ②는 구현 라운드
> `q3swz`가 넣었다. 시팅 18에서 층 24 한 런치가 2,765,883 → 2,319,186 사이클로 카드 밴드(2.14–2.50 M) 안에 들었고, 섹터는 하한보다
> 236개 많았다(rig-log 09-26#q3swz-ncu). ③ fstep은 열지 않았다. 시팅 18 뒤 long_scoreboard가 7.0 %로 5 %를 넘었으므로, 다음 레버는
> L2 순서(헤드 묶음 LPT, DRAM 재읽기 ≈ 55 MB)이고 fstep은 그 뒤에 본다.

시팅 16 결과(리드 메시지)를 받았습니다. 이 결과가 스펙의 "결과를 보지 못한다"는 줄을 대신하고, q3flashlit과 어긋나는 곳은 측정을 따랐습니다.


**결론.** 시팅 16으로 판이 바뀌었습니다. 1순위 레버는 FA2 스텝 모양이 아니라 **K/V 타일의 smem 행 배치**입니다. 우리 커널은 L2→SM 섹터를 1.5배 읽습니다.

- 행 피치가 272 B(256 + 16 B 패딩)라서 홀수 키 행이 32 B 섹터 경계에서 16 B 어긋나고, 이 행들의 cp.async가 섹터를 두 번씩 셉니다.
- 그래서 L2가 78 %로 가장 바쁜 유닛이 되었고, 이것이 long_scoreboard 18.1 %로 드러납니다. FA2는 2.1 %입니다.
- 순위: ① **S — 16 B 청크를 `row & 7`로 XOR 스위즐한 256 B 행**(비트 유지, S 크기, 예측 −8…−20 %), ② 프롤로그 다이어트(−2…−3.3 %), ③ fstep(S 뒤에만, 0…−7 %).
- 한 라운드에서 q3fa + S + 레버 3을 함께 착륙시키는 것을 권합니다.

## 0. 시팅 16이 바꾼 것 — 어긋난 q3flashlit 항

**틀린 항**
- **D0/D1 "L2→SM 바이트 같음"**: 틀렸습니다. 우리는 102,959,116섹터, FA2는 69,206,016섹터로 1.49배입니다.
- **cp 지연 상수(400, "가려진다")**: 틀렸습니다. 잔차의 주항은 long_scoreboard이고, 이 값은 main 7.4 % → q3fa 18.1 %로 **커졌습니다**. 커널이 빨라질수록 L2 벽에 먼저 닿았다는 뜻입니다.
- **FA2 텐서 86–96 %**: 실측 81.1 %입니다.
- **fetch 읽기와 드러난 MUFU·SHFL 사슬 읽기**: 둘 다 죽었습니다. no_instruction이 1 % 미만, short_scoreboard가 4.6 %입니다.
- **"q3fa가 평평했으니 잔차는 명령 수가 아니다"**: 틀렸습니다. 명령 수 절감이 L2 벽에 먹혔던 것입니다.

**맞은 항**
- DRAM/LRU 유도: K/V 재읽기 ≈ 55 MB, 측정 126 − 67(Q) − ≈1이 맞습니다.
- 그리드·HMMA 수가 같다는 점. 세 행 모두 텐서 busy가 **1.62 M 사이클로 같습니다**(1.6169 / 1.6226 / 1.6225 M). 이것이 아래 적합의 기준점입니다.

- 초과분은 main 33,621,936, q3fa 33,622,028입니다.
- 여기서 **Σhi × 8섹터**(키 하나·블록 하나마다 256 B)를 빼면 1,968 / 2,060이 남습니다. 이 잔여는 n_keys 읽기 규모입니다.
- 즉 초과분은 정확히 "살아 있는 키 행 하나당 256 B 한 번 더"입니다.

**배제한 후보**
- 중복 스테이징: q3fa 경로의 LDGSTS는 타일당 16개(8 + 8, `sass_inflight --step` 출력 `LDGSTS=16`)입니다.
- zero-fill: `U32x4::splat(0)`은 STS입니다(global 아님).
- 부분 타일: `hi`로 막혀 있습니다(`:301`).
- 워프 소스: 512 B 연속이고 256 B 정렬입니다.
- `.LTC128B` 대 `.BYPASS`: DRAM 쪽 힌트입니다. FA2 계수가 정확하므로 과다 계수의 원인이 아닙니다.

**기제** [가설, 두 커널 모두와 맞음]
- 가설: "LDGSTS의 L2 섹터 = (소스 32 B 섹터, 목적지 32 B smem 섹터) 쌍의 수."
- 우리 목적지 행은 272k B입니다. 홀수 k는 16 mod 32에서 시작하므로 소스 섹터마다 목적지 섹터 두 개에 걸쳐 2배, 짝수 행은 1배, 평균 **1.5배**가 됩니다(측정 1.500배, ±2 K 섹터).
- 경쟁 규칙 "목적지 128 B 줄 단위 분할"은 홀수 행 5/4, 짝수 4/4로 **1.125배**를 예측하므로 측정과 맞지 않습니다.
- FA2의 Swizzle<3,3,3>은 청크 쌍 (2j, 2j+1)을 같은 정렬 32 B 쌍으로 보냅니다. 두 규칙 모두에서 1배이고 측정과 맞습니다.
- **S는 두 규칙을 모두 만족**합니다. 쌍을 보존하는 XOR이고 128 B 반행 안에서만 움직이므로, 하드웨어가 어느 규칙이든 고치는 방법이 맞습니다.

**모형에 넣은 항(자원 시간선, q3fa 한 런치, 활성 2.746 M 사이클)**

| 자원 | 사용량 | 비율 |
|---|---|---|
| 텐서 | 1.62 M | 59 % |
| L2→SM 수요(피크 47.7섹터/clk 기준) | 2.16 M | **79 %, 최상위 유닛** |
| DRAM | 192 MB ≈ 0.45 M | ≈16 % |
| 발행 | 0.196/사이클/스케줄러 | |
| 호스트·PCIe·NVMe | 0 | |

- L2도 포화가 아닙니다. 벽시계는 **cp.async 도착 지연**입니다. 스텝의 사이클이 어느 유닛 수요와도 같지 않습니다.
- 버스트 계산 [유도]: SM당 K 버스트 = 24.2 KB × 2블록 ≈ 48 KB. 공정 몫 18 B/clk에서 약 2,690 사이클이 걸리는데, PV 덮개는 약 2,048 사이클이라 K 대기가 드러납니다.
- S 뒤: 32 KB → 1,780 사이클 < 2,048이 됩니다.

## 3. 기반 결정(스펙 1)

**q3fa를 기반으로 합니다.**
- 레지스터: 2블록/SM은 스레드당 65,536/(2×128) = 256 이하를 요구합니다.
  - main 255 → 256 × 32 × 8 = 65,536으로 한계에 딱 붙어 있어, 라이브 범위가 늘면 스필합니다(launch_bounds(128,2)).
  - q3fa 194 → 200 × 32 × 8 = 51,200으로 61레지스터 여유가 있습니다.
  - 예상 증가: S 기반 레지스터 +6–8, fstep +10–25 → **예측 210–230**.
- smem: 현재 34,816 + 1,024 = 35,840 × 2 = 71,680 ≤ 102,400. S 뒤에는 32,768/블록(−2 KB)이고, 3블록은 여전히 레지스터로 막힙니다.
- 병합 비용: q3fa의 두 파일 blob이 main에서 그대로입니다. `flash_gqa_prefill.rs` dd373d7…, `gate_qwen3moe_e2e.rs` b649cf0…, 베이스 ccdd3dc는 main 6778196의 조상. 충돌 0입니다.
- 비트: q3fa는 main과 비트 동일입니다(`docs/plan-triage.md:255` "비트 동일(새 ubatch `--dump` md5가 베이스와 같음)"). 그 `--dump` 확장이 이 라운드의 교차 빌드 비트 핀입니다.
- 결론: q3fa를 먼저 자기 커밋으로 착륙시키되, 같은 착륙 묶음에 S를 넣습니다.

## 4. S(스위즐) 설계 — 새 1순위

- **레이아웃**: 행 64워드(256 B). 물리 워드 = `row·64 + (((w>>2) ^ (row&7))<<2) + (w&3)`.
  - XOR은 청크 비트 0–2만 바꾸므로 128 B 반행 안에서 움직이고, 쌍 (2j, 2j+1)을 보존합니다.
  - `mma_row_words`는 다른 커널이 쓰므로 **건드리지 않고** 이 모듈 전용 상수와 헬퍼를 둡니다.
- **stage**: 스레드 청크 `ch = tid%16`, 키 `tid/16 + 8i`에서 `row&7 = (tid/16)&7`은 패스와 무관합니다.
  - 목적지 = 스레드 상수 `key0·64 + 4·(ch ^ ((tid/16)&7))` + i·512워드이므로 q3fa처럼 복사당 추가 명령이 0입니다.
- **LDSM**
  - QK: key&7 = lane&7이고 x = (lane&7) ^ ((lane/8)&1). kk의 오프셋 = `128·(kk>>2) + ((32·(kk&3)) ^ 16x)`. 이것은 kk&3에 대한 기저 4개(`tile + (row·256 + 16x) ^ 32j`)에 즉치 +128을 더한 것입니다.
  - PV `.trans`: x′ = (lane&7) ^ (lane/16)로 같은 꼴입니다.
  - Q 행 STS와 qa LDSM도 같은 규칙입니다. kk 순서(오름차순, 비트 계약)는 그대로입니다.
- **뱅크**: ldmatrix 한 위상은 연속 8행 × 같은 논리 청크입니다. 물리 청크 c^r이 한 반행에서 서로 다르므로 32뱅크를 한 번씩 씁니다. cp.async 쓰기는 워프당 512 B → 4 wavefront로 최소입니다.
- **비트**: 행마다 전단사이고 논리 청크마다 물리 자리가 하나입니다. ldmatrix가 같은 논리 16 B를 읽으므로 조각이 같고, 산술이 바뀌지 않습니다. 경쟁 표(5절)는 버퍼가 같아서 불변입니다.

## 5. fstep 설계(스펙 2·3 — 3순위로 유지)

**구조**
- 두 루프로 나눕니다. 이 구조는 블록 균일입니다.
- 카운트 루프에서 `blk_lo = min(8 counts)`를 구하고, `n_main = min(blk_lo/64, tiles−1)`로 둡니다(tiles = 0이면 0).
- **main 루프** kb < n_main: wait(0) → BAR1 → stage V(kb, 항상 full, 분기 없음) → QK → wait(0) → BAR2 → stage K(kb+1)(블록 균일 full/partial 분기, 라인 밖) → **무마스크 softmax + f select + 무조건 재스케일 + PV**. BAR2부터 역방향 가지까지 한 기본 블록이고, 셔플의 BRA.DIV만 앞에 남습니다.
- **tail 루프** kb ∈ [n_main, tiles): 같은 순서에 live 판정과 마스크 본문입니다.
- 시작 위치 p0 ≡ 0 (mod 8)이면 tail은 정확히 한 타일, 일반 p0이면 두 타일 이하입니다.
- vote(`warp::any`)는 없앱니다.

**단계 표**

| 단계 | KT | VT | 순서를 정하는 것 |
|---|---|---|---|
| wait(0) + BAR1 | K(kb) 도착·공개 | 모든 워프의 PV(kb−1) 읽기 완료 | BAR1 |
| stage V(kb) | | W (cp.async / zero STS) | BAR1 뒤, 읽는 이 없음 |
| QK(kb) | R | | BAR1 |
| wait(0) + BAR2 | 모든 워프의 QK 읽기 완료 | V(kb) 도착·공개 | BAR2 |
| stage K(kb+1) | W | | BAR2 뒤, 다음 읽기는 다음 BAR1 뒤 |
| softmax | 레지스터만 | 레지스터만 | — |
| PV(kb) | | R | BAR2. 다음 V 쓰기는 다음 BAR1 뒤 |

- 두 배리어 사이 구간은 {V 쓰기, K 읽기}와 {K 쓰기, V 읽기}로 버퍼가 서로 겹치지 않습니다.
- 한 스케줄러의 두 워프는 다른 블록 소속이라 smem을 따로 씁니다.
- wait_group(0)은 각 지점에서 미결 그룹이 정확히 하나입니다: BAR1은 K(kb), BAR2는 V(kb)를 닫습니다. FA2(`flash_fwd_kernel.h:417` / `:430`)와 같습니다.
- 프롤로그(Q STS → BAR → qa LDSM → BAR → K(0))는 불변입니다.

**예측 SASS(main 루프, K full, 워프-타일당)**
- HMMA 128. 비-HMMA ≈ 477 (465–490).
- 구성: FMUL 132 / FADD 66 / FMNMX 38 / HADD2 32 / MUFU 34 / F2FP 16 / LDSM 64 / LDGSTS 16 / LDS@!PT 6 / SHFL 4 / 제어 11–14(q3fa 33) / IMAD·ALU ≈ 45 / BAR 2.
- 구간별: 루프 머리~첫 QK 약 40, QK 구간 약 24, 드러나는 구간 170–230(FA2 201), **PV 그늘 200–260에 MUFU 20–24, FADD 50–56, F2FP 12**(FA2는 92에 21·26·12, q3fa는 22).
- 루프 약 9.7 KB, 연속.

**증명 방법**
- `seg.py` 구간 표에서 PV 그늘 MUFU ≥ 16, BAR 0.
- 실패하면 대안: 소스에서 PV의 kk2 루프 안에 pa[kk2+1]의 exp를 끼웁니다. 식과 l의 덧셈 순서가 같으므로 비트가 유지됩니다.

**비트 논증**
- (a) 오름차순 유지가 필수입니다. l = l·f + Σp̂와 PV 누산 순서가 계약이고(모듈 문서 `:38-47`), 내림차순이면 `--dump` md5가 바뀝니다. 떼어 낸 마스크 타일은 tail 루프 쪽 끝 타일이고, FA2의 `n_masking_steps`(`:334-338`)가 내림차순에서 앞 타일을 떼는 것과 같은 대각 타일입니다.
- (b) `f = m_new > m_old ? dev_exp(m_old − m_new) : 1.0`을 분기 없이(FSETP + FSEL, MUFU 무조건) 계산합니다. m 갱신도 같은 술어의 FSEL입니다. 이것은 현재 식 그대로입니다.
  - m_old = −∞ < m_new이면 dev_exp(−∞) = +0이 현재의 0.0과 같습니다.
  - −∞/−∞와 +∞/+∞에서는 select가 1을 고릅니다.
  - m은 NaN이 되지 않습니다. fmax가 NaN을 버리고 m은 −∞에서 시작하기 때문입니다.
  - ex2(±0) = 1이라는 사실은 **필요 없습니다.** FA2의 Check_inf 꼴(`softmax.h:75, :153-156`)이 성립하는 이유는 따로 있습니다: 같은 유한값의 x − x = +0(RN), +0 × log2e = +0, `ex2.approx.f32`(+0) = +1(PTX ISA 특수값 표).
  - o·f 무조건 곱은 main의 동작 그대로입니다. q3fa의 vote 생략과 main이 md5로 같습니다.
- (c) T가 8의 배수가 아니면 count 0인 행 때문에 blk_lo = 0 → n_main = 0이 되어 전부 tail로 갑니다. 같은 워프의 다른 행은 행 독립 산술이라 영향이 없습니다. 거부된 행은 프롤로그의 결함 기록과 끝의 `bad` NaN이 그대로입니다.
- **select는 출력으로 FAIL-first를 볼 수 없습니다.** 영향받는 상태는 count 0 행과 비유한 행뿐이고, 둘 다 출력이 NaN이거나 쓰이지 않습니다[유도].
- 교차 참조
  - llama.cpp MMA: softmax가 V 배리어 앞(`fattn-mma-f16.cuh:994-1003`, 박스 mainline).
  - exllamav3(`triton_paged.py:221-262`, 0740edc): 오름차순이고 사용자 배리어가 없습니다(Triton 파이프라이너, num_stages 3). Check_inf에 해당하는 것은 `m_exp = where(m_new==−inf,0,m_new)`(:248), `alpha = where(m==−inf,0,exp(m−m_exp))`(:251)입니다.

## (a) SASS 대조 — 레인별 목적지 오프셋

**q3fa 목적지 계산**(`q3fa_flash.sass` 역방향 슬라이스)
- `0x370 S2R R7, SR_TID.X` → `0xe410 R5 = tid·4` → `0xe420 R15 = tid>>4` → `0xe440 R6 = R5 & 0x3c` → `0xe470 R5 = R15·0x44 + R6` → `0xe540 R14 = R5·4`.
- 즉 목적지 = **key·272 + 16·(tid%16) B**입니다(key = tid/16 + 8i).

**두 스테이지 경로**
- V: `[R14+0x880·i]`, VT의 공유 오프셋 0 (`0xf310–0xf3f0`).
- K: `[R14+0x4400+0x880·i]`, KT의 공유 오프셋 17,408 (`0x130d0–0x131b0`).
- 프롤로그 K(0)의 full/partial 두 판본(`0xe5d0–0xe6b0`, `0xe7b0–0xeb90`)도 같은 꼴입니다.
- 0x880 = 2,176 = 8 × 272이고, 두 베이스 모두 32 B 정렬입니다.

**워프 한 번의 복사 = 행 2개**
- 레인 0–15는 짝수 키로, 목적지가 0 mod 32라 정렬됩니다.
- 레인 16–31은 홀수 키로, 272 ≡ 16 (mod 32)이라 소스 섹터(레인 2j, 2j+1)마다 목적지 32 B 섹터 두 개에 걸칩니다.
- 따라서 (소스 섹터, 목적지 섹터) 쌍은 8 + 16 = **24개**이고, 이상값은 16입니다. 1.500배입니다.
- 소스 쪽은 512 B 연속, 256 B 정렬이라 결함이 없습니다.
- 부분 타일: hi = t0 + 8은 짝수이므로 로드되는 키 0…hi−1의 짝수·홀수 수가 같습니다. 그래서 정확히 1.5배가 유지됩니다.
- main의 SASS도 목적지가 `key*ROW_W + 4*ch`로 같은 레이아웃입니다(술어가 붙은 판본 `R178…R205`). 계수가 main 102,959,024 / q3fa 102,959,116으로 같은 것과 맞습니다.

**gemm_q4k 소스 페이지**(`…082817.source.csv`)
- qs 복사(`[R104+0x10]`, `[R104+0x1410]` = 64행 × 80 B 떨어진 두 절반)에서 Theoretical/Ideal이 `778176/444672 = 1.75`, `1038336/638976 = 1.625`, `898560/559104 = 1.607`입니다.
- 쌍 규칙으로 유도하면 [유도]:
  - 소스 qs는 `144·sb + 16 + 64·hh`에 있어, 짝수 sb면 16 mod 32, 홀수 sb면 0입니다.
  - 목적지 qs는 `row·80 + 16`에 있어, 짝수 행이면 16 mod 32, 홀수 행이면 0입니다.
  - 짝수 sb: 행당 쌍 3과 4 → 평균 3.5/2 = **1.75**.
  - 홀수 sb: 4와 2 → **1.5**.
  - 반반 섞이면 **1.625**.
- 소스만 보는 규칙은 짝수 sb 1.5, 홀수 sb 1.0이라 1.75를 만들 수 없습니다. 따라서 ncu의 이 지표는 목적지를 반영하고, gemm 결과는 소스 항을 분리한 뒤에도 독립 증거로 남습니다.
- 4 B `LDGSTS.E`(≈ 7.9배)와 16 B 헤더(2.0배)는 크기 효과이므로 여기서 다루지 않습니다.

**(e) 반박할 계수 없음**

## (b) 스위즐 레이아웃 — K, V, 그리고 KT를 거치는 Q

**배치**
- 행 64워드(256 B), 타일 16 KB입니다. 물리 워드는 `row·64 + (((w>>2) ^ (row & 7)) << 2) + (w & 3)`입니다. 청크 c는 `c ^ (row & 7)`로 가며, 청크 비트 0–2만 바뀌므로 128 B 반행 안에서만 움직입니다.
- smem은 블록당 34,816 → 32,768 B(−2 × 64 × 16)입니다. 2블록 = 2 × (32,768 + 1,024) ≤ 102,400이고, 3블록은 여전히 레지스터(194 > 168)로 막힙니다.
- `flash.rs:207` `mma_row_words`는 다른 커널이 공유하므로 **건드리지 않습니다.** 이 모듈 전용 상수와 헬퍼를 두고, `flash_gqa_prefill.rs:100`의 단언은 이 레이아웃의 단언으로 바꿉니다.

**cp.async가 섹터 하나에 머무는 증명**
- 쌍 (2j, 2j+1)은 같은 행(`row & 7` 동일)에 있습니다.
- (2j)^r과 (2j+1)^r은 비트 0만 다르므로 = {2m, 2m+1}, m = (2j^r)>>1입니다. 즉 정렬된 32 B 목적지 섹터 하나에 들어갑니다(반쪽 순서만 바뀔 수 있음).
- 소스의 128 B 줄 하나도 목적지 128 B 반행 하나에 들어가므로, 128 B 줄 규칙에서도 1배입니다.
- 스레드별 목적지 = `key0·64 + 4·(ch ^ ((tid/16) & 7))` + i·512워드입니다. 패스 i가 key의 비트 0–2를 바꾸지 않으므로 스레드 상수가 되고, 복사당 추가 명령이 0입니다.

**ldmatrix 무충돌 증명**
- 한 위상은 8레인 = 연속 8행(`row & 7`이 0…7 전부)이 같은 논리 청크 c를 읽습니다.
- 물리 청크 c^r은 서로 다른 8개이고 한 반행 안에 있으므로, 8 × 16 B = 128 B가 32뱅크를 한 번씩 씁니다.
  - K(plain): key = 16nj + lane%8 + 8(lane/16), c = 2kk + (lane/8)%2 → row & 7 = lane & 7.
  - V(`.trans`): key = 16kk2 + lane%8 + 8((lane/8)%2), c = 2nd + lane/16 → 같은 꼴입니다. `.trans`는 레지스터 분배만 바꾸고, 행 주소 8개와 16 B 연속성 요구는 plain과 같습니다.
  - qa(Q 조각): row = wid·16 + lane%16, c = 2kk + lane/16 → 같은 꼴입니다.
- Q의 STS(프롤로그): 워프는 한 행의 연속 32워드 = 반행 8청크를 씁니다. 스위즐 후에도 같은 반행의 서로 다른 8청크이므로 32뱅크를 한 번씩 씁니다.
- cp.async 쓰기는 워프당 512 B = 4 wavefront로 최소입니다.

**주소 비용**
- kk의 바이트 오프셋 = `128·(kk>>2) + ((32·(kk & 3)) ^ 16x)`, x = (lane & 7) ^ b입니다(K는 b = (lane/8) & 1, V는 lane/16).
- 레인별 기저 4개(`tile + ((row·256 + 16x) ^ 32j)`, j = 0..3)에 즉치 +128이면 됩니다. K와 V 합쳐 레지스터 +8, LDSM당 추가 명령 0입니다. XOR을 타일 안 오프셋에서 하므로 smem 베이스 정렬 조건이 필요 없습니다.
- kk와 kk2의 오름차순은 그대로입니다(HMMA 누산 순서가 비트 계약).

**비트 불변**
- 스위즐은 행마다 청크 번호의 전단사이고 16 B 단위라, 각 논리 16 B는 연속·16 B 정렬 상태로 물리 자리 하나를 갖습니다.
- 스테이지는 모든 논리 청크를 정확히 한 번 쓰고(cp.async 또는 zero STS), ldmatrix의 각 레인 주소는 이전과 같은 논리 (행, 청크)를 가리킵니다.
- 그래서 받는 조각이 같고, 산술은 한 줄도 바뀌지 않습니다.
- 경쟁 표(앞 보고 5절)는 버퍼 KT·VT와 배리어 위치가 같아서 그대로입니다.
- 확인은 flash 게이트(행 단독 비트, NaN 패딩, 결함 행)와 e2e `--dump` md5를 main과 비교하는 것으로 합니다.
