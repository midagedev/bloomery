# V4.1 B5 설계와 라운드 절단 — b5plan 원문 보고

읽기 전용 설계 라운드 b5plan(opus, 2026-09-23)의 보고를 그대로 옮겼다. 결정과 라운드 순서는 [`plan.md`](../plan.md)의 「B5 라운드」가 정본이고, B5 라운드의 스펙은 여기의 노드 표(§1), 상태·파라미터 표(§2), 게이트(§4.1)를 복사해 간다. 노드 모델은 [`v41-b5-plan/nodes.py`](v41-b5-plan/nodes.py)(`python3 nodes.py <깊이>`)와 `bykind.py`(§1.3의 층 종류별 합)로 다시 돌릴 수 있다 — 저장소로 옮기면서 임계 표시 두 줄을 §1.3의 B5 기준 배치(`engram_wkv`는 0층 그늘, HC_PRE(attn)는 임계)에 맞췄다. 보고 안의 `b5plan/`·`lead-b11b/`·`wave-m3/` 경로는 세션 스크래치라 남아 있지 않을 수 있다.

---

읽기 전용 라운드였다. 기준은 main `0e15d4f`이고, 라운드 도중 `docs/oracle.md`에 디코드 스텝 세트 절이 들어와 게이트 설계에 반영했다. 저장소와 박스에는 아무것도 쓰지 않았다. 노드 모델 스크립트는 세션 스크래치 `b5plan/nodes.py`와 `bykind.py`다(저장소 밖, `python3 nodes.py <depth>`로 다시 돌릴 수 있다).

**요약**
- **(a)를 먼저 올린다.** 예측은 R1 40.6 ms(24.6 tok/s), 직렬 44.4 ms(22.5 tok/s)다. 조건은 n=1, 깊이 4096, A6000 + 호스트다 [유도].
  - A6000 재측정 전의 ik 선 20.4–20.7보다 약 20 % 높다. B5의 tok/s 목표는 (a)만으로 닫힌다.
  - (b)는 +~10 %지만 A2-2가 끝난 뒤에야 가능하다.
- **스텝 하나가 캡처 그래프 하나다.** 노드는 1,068개(커널 988 + memop 80)다.
  - 그래프 안에서 호스트를 기다리는 자리는 층마다의 expert 합류 40개뿐이다.
- **GPU 임계 경로는 12.95 ms, 호스트 다리는 26.54 ms(토큰의 65 %)다.**
  - `engram_wkv`는 토큰 id에만 달려 있다. 그래서 0층 호스트 다리가 도는 동안 GPU가 쉬는 시간(이하 "그늘")으로 옮길 수 있고, 설계만으로 −0.51 ms를 얻는다.
- **PPL 패리티 목표는 2.2355가 아니다.** 2.2355는 plain Q3_K_M 파일에서 결함을 가진 채 잰 값이다.
  - 서빙 파일에서 고친 ik는 **1.8989 ± 0.0491**이다(4청크, 118 s) [측정 `/root/bloomery-data/ikppl/after-idxkey.log`, rig-log `log/2026-09-23.md:301`].
- **라운드는 8개이고 model.rs를 점유하는 것은 b5load 하나다.**

### 2.2 스텝 파라미터

V2-Lite는 `refresh`가 `[token, pos, pos+1, cs…]`를 H2D 한 번으로 `step_params`에 올리고, 캡처된 커널이 그 고정 포인터를 읽는다(`arch/deepseek2/mod.rs:199-215`). V4.1도 같은 구조에 이미지만 커진다.

| 항목 | 바이트 | 계산하는 쪽 |
|---|---:|---|
| token, pos, 창 칸(pos%128), 창 길이 | 16 | 호스트 |
| csa와 hca 각각: state_read×r, state_write, write_pos, persist src/dst, 완성 플래그, n_vis, min(n_vis, top_k) | ~72 | 호스트 `plan.rs`(b4plan2, ik `src/llama-dsv4.cpp:664-832`의 전사) — 계획 산술의 소유자는 하나다 |
| rope 표 3개 × 32쌍 f32: T_A(pos, 10k, 0·1층), T_B(pos, 160k YaRN), T_C(csa 행 위치 pos−1, 160k YaRN) | 768 | 호스트(b4rope 표) |
| 임베딩 bf16 행 | 10,240 | 호스트(`token_embd`는 호스트에 있다, `v41-placement.md:90`) |
| engram 행 2사이트×24×272 B | 13,056 | 호스트(`crates/engram`) |
| **합** | **~24.2 KB/스텝** | H2D 1회 ~5 µs [가정] |

ik가 올리는 f16 마스크는 우리는 올리지 않는다(d1 input 행 기준: `dsv4_raw_mask_padded` 16 KB, `csa/hca_kq_mask` 1–2 KB). 개수가 마스크를 대신한다.

### 2.3 정적 그래프로 가능한가: 가능하다

스텝마다 달라지는 것과 그것을 고정하는 방법은 다음과 같다.

| 달라지는 것 | ik | 우리 설계 |
|---|---|---|
| 압축 행 출현 | 그룹이 끝날 때만 노드가 생긴다 | compress·index_key가 매 스텝 돌고, 완성 플래그가 설 때만 행과 키를 쓴다 |
| 인덱서 | `top_k < pad256(n_vis)`일 때만 짓는다(`src/graphs/build_deepseek4.cpp:1344-1348`). 그래서 hca는 pos ≥ 512, csa는 pos ≥ 1025부터 고른다 | 인덱서 노드를 늘 둔다. n_vis ≤ top_k면 점수 커널은 조기 종료하고 top-k 커널은 항등 id를 쓴다. 두 조건이 같은 행 집합을 고른다 [유도]. top_k 64 덮어쓰기에서 −inf 행은 attention에서 0이 된다 |
| 고른 행 수·창 길이 | 마스크 폭(n_kv 패딩) | 개수를 파라미터에서 읽는다. 격자는 ctx_max 기준으로 고정하고 빈 세그먼트는 조기 종료한다(V2-Lite flash가 n_keys를 디바이스 버퍼로 받는 방식, `dispatch.rs:384-534`) |
| attention 경로 | T=1이면 id gather | 압축 행은 늘 id 목록으로 읽는다(H2 한 경로). 1단계의 H1 prefix는 발판이고, 2단계 뒤에는 경로를 하나만 둔다 |

- **노드 수 예측**: 1,068이다(단일 스트림, 이 입도). 감사 K1·K3·K6 융합을 하면 ~850이 된다.
- **구조 게이트**: 캡처 노드 수와 memop 80개는 컴파일·캡처 시점의 래칫이다. `graph.rs:156`의 `nodes()`가 kind를 돌려준다.
- **그늘 배치**: 스트림 순서를 `… 라우터 → go → [HC_PRE(ffn), shared, GPU expert, (0층에서만) engram wkv 2개 + 키 norm] → wait → combine → HC_POST`로 둔다.
  - `engram_wkv`는 `emb = get_rows(engram_embd, rows)`에만 의존한다(`build_deepseek4.cpp:1005-1010`, q 쪽만 스트림을 읽는다 `:1030`). 그래서 0층의 850 µs 호스트 다리 그늘(GPU가 할 일은 67 µs뿐)에 들어간다.
  - HC_PRE(s)는 지연(lag) 규칙 때문에 s의 본문에 필요하지 않다. s의 HC_POST와 s+1의 접기에만 필요하다(`:626-667`의 `pre_in`, `:1529-1539`의 원핫 초기값, `:1559-1565`).
  - 그래서 ffn 쪽은 `go` 뒤에 둘 수 있다. attn 쪽은 갈래 스트림이 없으면(`graph.rs:60-133`은 단일 스트림 캡처) 임계 경로에 남는다.

### 2.4 그래프가 호스트를 기다리는 곳

- **(a) 설계에서는 expert 합류 40개(memop 80)뿐이다.**
  - 층 안의 top-6가 전부 GPU 슬롯일 확률은 C(62,6)/C(384,6) ≈ 1.4e-5다 [유도, 균등 라우팅 가정]. 합류를 정적으로 뺄 수 없다.
- 라우팅과 top-k는 디바이스에서 끝난다. 계획 정수·rope·임베딩·engram 행은 런치 전에 호스트가 만들어 H2D로 올린다.
- 토큰마다 한 번 있는 argmax 동기화는 그래프 사이에서 일어난다(`model.rs:525-532`와 같다).
- 선택지에 따라 대기가 늘어나는 경우:
  - engram 조회를 0층과 겹치면 −0.31 ms 대신 대기가 1개 더 생긴다.
  - (b)는 카드 넘김(스트림 80 KB, 호스트 경유 [가정: GeForce와 A6000 사이 P2P는 미확인])이 생긴다.
  - (b′)는 3090 expert 서버가 카운터의 두 번째 작업자가 된다.

### 3.2 engram

- **"한 스텝 앞서"는 성립하지 않는다.**
  - 24개 행 id의 롤링 해시가 모두 현재 토큰에서 시작한다(`ctx[0] = map_of(batch.token[i])`, ik `src/llama.cpp:5403-5415`).
  - 가장 이른 시점이 앞 스텝의 argmax 직후다.
- **B5 기준 설계**
  - 런치 전에 스텝 스레드에서 조회한다(0.31 ms [측정 `v41-placement.md:236`]).
  - 행 13,056 B는 파라미터 H2D에 싣는다.
  - GPU는 0층 그늘에서 wkv와 키 norm을 돌리고, 1·14층에서 스트림 4개에 게이트를 곱해 더한다(`build_deepseek4.cpp:985-1047`).
- **나중 레버(−0.31 ms)**: 런치를 먼저 한다. 0층 attention(~0.29 ms) 동안 호스트가 조회해 매핑 메모리에 쓰고, wkv 앞에 flag 대기를 하나 둔다.

- **게이트 범위**
  - b4engram이 거는 것은 게이트 커널(키/쿼리 norm, 스트림별 점수, 부호 제곱근 sigmoid, 층 1·14)뿐이다(`spec-b4engram.md:21-33`).
  - B5가 더할 것: 호스트 행 id = 오라클 int input 행 `engram_rows-{1,14}`(i32×24, 정수 비트 동일, CPU), 그리고 사슬의 `engram_out`.

### 3.3 PPL과 프리필

**ik 측정 조건** [측정 박스 로그, 읽음 `tools/ref/ik-ppl.sh:159-160`]
- wikitext-2-raw `wiki.test.raw`, `-c 2048 -b 2048 --chunks 4`, CPU만, `-t 32`, `--defer-experts`
- `first = n_ctx/2`(`examples/perplexity/perplexity.cpp:668`), 청크마다 KV를 비운다(`:679`). add_bos는 false다.
- 채점 토큰은 4 × 1,023 = 4,092개다.
- 서빙 파일 결과:
  - 결함 트리 1.9027 ± 0.0493(136 s)
  - 고친 트리 **1.8989 ± 0.0491**(118 s). 청크 누적값은 [1.5930, 1.4993, 1.4939, 1.8989]다.
- 2.2355 ± 0.0626은 plain Q3_K_M 324 GB에서 잰 값이다(rig-log `log/2026-09-16.md:27`).

**프로토콜**
1. **ik 쪽**: 고친 트리(49ef19d0)에서 `--kl-divergence-base <file>`로 돈다(`common.cpp:2389-2391`).
   - PPL 1.8989를 재현하는지가 도구 검증이다.
   - 파일에는 토큰(n_chunk×n_ctx i32)과 채점 위치마다 전 어휘 log-prob(uint16 양자, 최대값에서 24 nat 아래로 자름, `perplexity.cpp:219-226`)가 들어 있다.
   - 크기는 4청크 ~1.06 GB, 16청크 ~4.2 GB다 [유도]. 우리 쪽에는 토크나이저가 필요 없다.
2. **우리 쪽**: 파일에서 토큰을 읽는다. 청크마다 reset하고 m=1로 2048스텝을 돈다. 채점 위치에서 다음을 모은다.
   - NLL, KLD(ik‖우리), top-1 일치, ik와 우리의 top-2 마진
   - 짝 차이 d = NLL_우리 − NLL_ik의 평균과 SE
3. **벽시간**: 4청크는 8,192스텝 × 40.6 ms = **5.5분** + 적재다(적재 시간은 미측정, b1b 게이트가 기록한다). 16청크는 22분이라 적재까지 포함하면 30분 경계다. test 전체는 몇 시간 규모라 승인 대상이다(이 토크나이저로 토큰 수는 세지 않았다).
4. **밴드** [유도, V2-Lite σ가 V4.1에 옮겨진다고 가정]
   - σ_rel = √(0.378² + 0.271²) ≈ 0.47 logit이다. 로짓당 잡음 s ≈ 0.33이 나오고, 위치 혼합을 가정하면 sd(d) ≈ 0.1–0.2 nat다.
   - 2SE는 4청크에서 **±0.3–0.6 %**, 16청크에서 ±0.15–0.3 %다.
   - 거친 반올림 규칙의 편향은 E[ΔNLL] ≈ ½(s_o² − s_i²)(1 − Σp²) → **+0.2…+0.9 %**다.
   - 버그 판정: 4청크에서 Δ_PPL > +1.5 %면 빨강이다.
   - ik가 자기 값에 붙인 ±0.0491(2.6 %)은 짝 없는 SE라서 비교의 해상도가 아니다.
   - 첫 실행이 sd(d)와 σ_rel을 직접 잰다. 유도와의 틈이 그 라운드의 발견이다.
5. **대조군**: ik 대 ik(-b 512 대 2048, 또는 융합 top-k 켬/끔)를 CPU로 약 2분씩 돌려 경로 차이만으로 생기는 KLD 바닥을 잰다.
6. **조기 판정 c512**: `-c 512 -b 512 --chunks 16`(채점 16 × 255 = 4,080)으로 돈다. 두 엔진 모두 이 조건에서는 인덱서를 짓지 않는다(pad256(n_vis) ≤ 512). 그래서 1단계 bring-up만으로 패리티를 본다. 우리 쪽 벽시간은 5.5분이다.

**A5는 패리티보다 먼저일 필요가 없다.** m=1로 4청크가 6분이면 된다. A5는 서빙 TTFT의 문제다.

## 4. 게이트와 절단

### 4.1 게이트

- **G1 스텝 게이트(상태 주입)**
  - 세트: `ref_deepseek41_step4_every_node`(pos 4), `…_d1_every_node`(pos 301, top_k 64 덮어쓰기), `…_d2_every_node`(pos 1025, top_k 512), `-unfused` 쌍.
  - 방법: 세트의 input 행을 우리 레이아웃으로 옮겨 싣고, pos를 맞추고, 한 스텝을 재생한다. input 행은 `cache_k_l*`와 압축기 상태 leaf(읽는 노드의 src0/src1로 찾는다, `docs/oracle.md` 새 절), 압축 행, 인덱스 키, `dsv4_*` 정수다. ik raw 셀은 마지막 128행만 링으로 옮긴다.
  - 핀은 사슬의 계약만 건다. op 핀은 B4에 있으므로 두 번 걸지 않는다(AGENTS "one test per contract").
    - 라우터 id: 정수 일치(경계 근접 동률 제외, b4moe 규칙)
    - top-k id: 집합 일치(512번째와의 거리가 밴드 안이면 제외, `-unfused` 점수로 판정)
    - 층별 스트림 상대오차: B4 밴드를 전파해 유도한 포락선
    - `result_output`: top-1과 마진
  - 노드별 대조는 진단으로 출력만 한다.
  - top_k 덮어쓰기는 hparams에서 게이트 전용 인자로 받는다.
  - **1단계용 변형을 새로 덤프할 것을 제안한다.** `d1n`: 프리필 301, 파일의 top_k 512, `-c 512`로, 선택 없이 깊이 301과 창 자르기를 본다. 프로필에 한 줄을 추가하고 CPU 임대로 몇 분 돌리면 된다.
- **G2 구조**: 캡처 노드 수가 예측 표와 같고 memop이 80개인지 본다. 캡처 시점 래칫이다.
- **G3 greedy**: ik(고친 트리, CPU) greedy 64토큰 대 우리를 비교한다. 첫 불일치 위치에서 우리 마진이 1.5(≈3σ_rel) 미만이면 통과다 [유도]. 1단계는 pos < 512에서 본다.
- **G4 PPL/KLD 패리티**: §3.3의 프로토콜이다. c512 16청크는 1단계 뒤, c2048 4청크는 2단계 뒤에 돈다.
- **G5 forced_ik(V2-Lite forced_exact에 해당하는 것)**
  - 같은 실행의 채점 위치에서 argmax가 어긋나고 ik 마진 ≥ 0.5인 위치를 센다.
  - 핀은 ≤ E + 3√E다. E = Σ Φ(−m_i/σ_rel)이고, σ_rel은 같은 실행에서 (우리 마진 − ik 마진)의 RMS다.
  - 버그를 잡는 핀이지 정밀도 순위가 아니다(plan.md "성능이 먼저").
  - f64 V4.1 심판은 L 크기라 B5 밖에 둔다.
- **G6 V2-Lite 불변**: b5load는 이동 클래스다. `just ptx-scan` 표가 같고, e2e 세트가 같고, `gate-gpu-e2e` 개수 핀이 그대로여야 한다.
- **tok/s는 리드가 잰다**: 같은 임대에서 ik와 우리 (a)를 깊이 6/1024/4096으로 잰다.

### 4.3 병렬성과 순서

- 지금 시작: b5meta ‖ b5ppl(도구).
- b2b 머지 뒤: b5load ‖ b5host.
- b5load 뒤: b5attn ‖ b5ffn ‖ b5glue. 파일이 분리돼 있고, op가 도착하는 대로 시작한다.
- 그다음: b5step → b5index.
- **model.rs를 만지는 B5 라운드는 b5load 하나다.** 그래서 plan.md:377의 "B5 → A5"를 "b5load → A5 ‖ B5의 나머지"로 풀 수 있다.
- 1단계에서 인덱서를 뺄 수 있다. 다만 **압축기와 인덱스 키 쓰기(b4-comp)는 pos 0부터 필요하다.**
  - hca는 비율이 1이라 20층이 pos 0에 행 0을 쓰고, 20–39층이 그것을 읽는다.
  - pos ≥ 512의 인덱서는 그 앞의 키 전부를 읽는다.
- V4.1 전체 모델 게이트는 적재하는 동안 3090 게이트 락을 잡는다. 무거운 V4.1 게이트 라운드는 한 번에 하나만 돌린다.
- 30분 규칙: 게이트는 모두 30분 안이다. c2048 16청크만 적재까지 포함하면 경계다.

## 5. 브리프 §2의 질문 셋

1. **V2-Lite 가정 가운데 깨지는 것**
   - KV가 층마다 한 종류다(`arch/deepseek2/mod.rs:58-60`).
   - N_EXPERT가 64다(`router.rs:30`, `moe.rs:150`).
   - 잔차가 벡터 하나이고 층마다 8 KiB D2D 복사를 한다(`dispatch.rs:28-33,67-72`). V4.1은 스트림 4개와 지연 mix다.
   - 적재가 Gguf 하나다(`model.rs:301`). 스테이지도 하나다(`model.rs:504`).
   - 임베딩이 GPU의 Q3_K 행이다(`dispatch.rs:99-103`). V4.1은 호스트 bf16 행이다.
   - rope 표가 하나다(`mod.rs:204`). V4.1은 셋이다.
   - MMA 폭이 576이고 sink가 없다(`flash.rs:158`).
   - Q8Act k ≤ 10944다(`tensor.rs:106`). V4.1의 hc_fn은 K=20480이다.
   - `_sel` 범위 밖 슬롯에 이전 값이 남는다(`lib.rs:1269-1272`).
   - shared 융합 커널이 q3_K 전용이다(`fused.rs:716-720`). V4.1은 q8_0 + 클램프다.
   - SwiGLU에 클램프가 없다(`qdot/src/lib.rs:2606`).
   - `AnyEngine`이 crates/gpu에 있다(`engine.rs:18-20`, 순환 문제).
   - `seed_depth`는 V4.1의 여러 스트림(창·압축 행·키·상태)을 일관되게 채우지 못한다.
   - 스텝 안에 호스트 서비스 루프가 없다(`model.rs:525-532`).
   - 헤드 타입(Q6_K 검사 `head.rs:31-40`)은 그대로 맞는다. 바뀌는 것은 입력(`hc_out`)과 어휘 크기다.
2. **헤드**: `output.weight`는 Q6_K [5120 → 129,280], 542,976,000 B다 [읽음 헤더].
   - q6k 776.0 µs(700 GB/s) [측정 A6000] + rms 7.4 + Q8 2.1 + 블록 하나짜리 argmax 53.9 [유도] = **~0.84 ms, 토큰의 2.1 %**다.
   - argmax를 여러 블록으로 나누면 ~0.79 ms다.
3. **합류 말고 호스트를 기다리는 곳**: 없다(§2.4).
   - top-k와 라우팅은 디바이스, engram id와 계획 정수는 런치 전 파라미터로 온다.
   - engram 겹침 레버, (b) 넘김, (b′) 서버를 고르면 대기가 늘어난다.
