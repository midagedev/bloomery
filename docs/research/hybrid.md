# CPU·GPU 공동 실행 — 이론 상한과 엔진 현실의 종합

2026-09-21. 두 조사를 맞댄 글이다: 엔진 소스 독해([`hybrid-engines.md`](hybrid-engines.md))와 문헌·형식 모델 조사(opus 서브에이전트, 원문 [`hybrid-lit-report.md`](hybrid-lit-report.md)). 여기의 시간은 전부 **유도값**이고, 아래 "흔들리는 전제" 절의 두 대역폭에 매여 있다. 리드가 원본에서 확인한 것: WKS-36 실행의 배치와 모델 파일(rig-log `log/2026-09-19-verification-does-not-amortise.md` 3행, `configs/v41-serve.sh`), HybriMoE가 전문가를 통째로만 배정한다는 것(arXiv 2504.05897 본문), HeteGen의 α 분할이 dense OPT와 전송 비용에 대한 것이라는 것(arXiv 2403.01164 본문), KTransformers의 Expert Deferral과 "평균 정확도 하락 0.5% 이하"(SOSP'25 초록). KTransformers의 "공유 전문가가 GPU 시간의 18%"와 "건너뛰기 13.3%"는 조사만 읽었고 리드는 확인하지 않았다. arXiv 2505.16056에서 뽑은 수치는 조사 스스로 열 어긋남을 의심했으므로 옮기지 않는다.

## 모델

디코드 한 스텝은 층 40개의 **사슬**이고, 층마다 두 프로세서가 갈라졌다 합치는 모양이다. 층 ℓ의 전문가는 층 ℓ−1의 출력을 기다리므로 한 시퀀스 안에서 층을 가로지르는 겹침은 정확하게는 불가능하다. 그래서 상한이 둘로 갈린다.

- 일량 상한: `T ≥ max(C, G)`. 호스트 항 C = 22.6 ms, GPU 항 G = 33.9 ms, r = C/G = 0.67이면 겹침의 최대 이득은 `1 + min(r, 1/r)` = 1.67배. **이건 처리량 숫자다** — 독립 시퀀스가 둘 이상 있어야 닿는다. 어떤 r에서도 2배를 넘지 못한다.
- 임계 경로: `T ≥ Σ [D_ℓ + max(c_ℓ, s_ℓ)]`. s_ℓ은 같은 층에서 호스트 전문가와 **무관한** GPU 일이고, 단일 시퀀스의 지연은 이쪽이 정한다.

`hybrid-engines.md`가 "GPU는 토큰의 40%, CPU는 60%를 논다"고 쓴 것은 일량 상한의 그림이다. 단일 스트림에서 그 유휴를 다 메울 수는 없다 — 메울 수 있는 몫은 s_ℓ 크기만큼이다.

## 단일 스트림에서 실제로 얻는 것 (β_h 147.7, β_g 247, 출력 불변)

조사는 공유 전문가를 라우팅 전문가와 같은 크기(16.85 MB)로 가정했다. 우리 파일에서는 q8_0 37.6 MB다(`hybrid-engines.md`). 그 값으로 다시 계산했다: 공유 전문가 0.152 ms, 그것을 뺀 층당 GPU 일 0.623 ms, 호스트 전문가 0.684 ms.

| 방법 | 스텝 | 배수 |
|---|---:|---:|
| 오늘(직렬, 블록 단위 배치) | 56.5 ms | 1.00 |
| 공유 전문가를 호스트 다리와 겹침 | 51.4 ms | 1.10 |
| + 전문가 행 분할, VRAM 용량 한도(전문가 바이트의 23%가 GPU) | 46.0 ms | 1.23 |
| + 행 분할, VRAM이 공짜라면 | 39.0 ms | 1.45 |

(조사 원문의 같은 행은 1.04 / 1.15 / 1.37이다. 차이는 공유 전문가 크기 하나다.) 첫 행은 엔진 조사의 R1(−5.6…−10.4%)과 같은 말이다.

## 전문가를 종으로 가르기

SwiGLU 전문가는 뉴런에 대한 합이므로 `gate`/`up`의 행과 `down`의 열을 같은 뉴런 경계에서 나누면 두 부분합의 합이 원래 출력이다. 부동소수 합산 순서만 달라진다 — 게이트는 비트 동일이 아니라 밴드다(`q_nope2` 셀 분할과 같은 급). `down`은 행 방향 블록 양자화라 뉴런 경계가 블록 크기(256)의 배수여야 한다.

리드가 조사 전에 적어 둔 논증은 유지된다: **기대 비용**으로는 이득이 없다. 라우팅이 균일하면 "전문가의 23%를 GPU에 두기"와 "모든 전문가의 23%를 GPU에 두기"는 토큰당 호스트 바이트가 같다. 이득은 전부 `max()`에서 온다 — 통째 배치는 층마다 GPU에 걸린 전문가 수가 0~6으로 흔들려 두 다리가 어긋나고, 행 분할은 매 층 매 토큰 같은 비율로 맞는다. 예측이 필요 없고, 빗나감이 없고, 검증 배치 폭 k에 무관하다. 분할 가능 부하(divisible load) 이론의 표준 결과 — 끝나는 시각을 맞추는 분할이 최적 — 그대로다.

문헌의 빈칸이기도 하다(리드 확인): HeteGen은 α 분할을 dense 층에, 그것도 **전송 비용**에 대해 유도한다. HybriMoE는 전문가를 통째로 GPU 큐 아니면 CPU 큐에 넣는다. KTransformers는 NUMA 소켓 사이에서만 나눈다. GPU에 **상주하는** 가중치로 MoE 전문가를 CPU/GPU 사이에 나눈 것은 조사가 읽은 범위에 없다. 조사가 열지 못한 CoX-MoE(arXiv 2605.17889)가 제목으로는 같은 기제다 — 읽기 전에는 "없다"고 말하지 않는다.

**전제 조건.** 오늘의 직렬 실행기 위에서는 이득이 0이다. 호스트 다리와 GPU 다리가 동시에 돌아야 하므로 그래프 안의 경계(엔진 조사의 R2)가 먼저다. 순서는 R2 → 공유 전문가 겹침 → 행 분할 스윕(호스트 몫 x = 0, 0.4, 0.6, 0.77, 1.0)이고, 곡선의 최소가 `β_h/(β_h+β_g)`의 용량 한도 값에 오면 모델이 맞은 것이고 평평하면 경계 비용이 지배한다는 뜻이다. 그리고 VRAM 1%p는 약 0.27 ms/스텝이다 — engram을 NVMe에 두는 것과 KV 양자화가 용량이 아니라 속도의 레버가 된다.

## 배치를 다이나믹하게 조정하기

전문가 크기가 같으므로 정적 최적은 "활성 확률 큰 순으로 채우기"다. 동적 정책이 이기려면 확률이 치우쳐 있거나 시간 국소성이 있어야 한다. V4.1의 라우터는 그 반대를 향해 학습됐다: 선택 전용 편향으로 부하를 평평하게 맞추고, 공유 전문가가 공통 신호를 가져가고, N/k = 64라 두 토큰의 우연 겹침이 k²/N = 0.094개다. 균일하면 적중률은 캐시 비율과 같다(23%). 문헌의 실측은 128전문가 Qwen3-30B-A3B에서 캐시 13.4%에 LRU 65.9%·Belady 79.1%(arXiv 2608.18261)인데 256~384 전문가 라우터를 잰 글은 조사가 찾지 못했다. 더 나은 정책의 몫은 HybriMoE 실측으로 25% 용량에서 +6~8%p — 우리 스텝의 약 3%다.

전송 대 호스트 연산은 의견 차이가 아니라 손익분기 하나다: 전문가 하나 올리기 0.64 ms 대 호스트에서 계산 0.114 ms, 비율은 정확히 β_h/β_link = 5.6배이고 배치가 수백 토큰을 넘어야 뒤집힌다. 그래서 대배치 논문은 가중치를 흘리고 배치 1 논문은 호스트에서 계산한다. 예측·프리페치는 가중치가 이미 DRAM에 있는 우리에게 ≈0이다.

엔진 조사의 R3 괄호(−27.8…−9.3%)는 적중률 0.5를 가정했다. 평평한 라우터에서는 0.23~0.33이 더 그럴듯하므로 **그 괄호는 낙관이다.** 판정은 싸다: 라우터 id 덤프(GPU 불필요)로 p 히스토그램, 적중률 곡선(정적·LRU·Belady), 인접 토큰 겹침, k = 1..8의 서로 다른 전문가 수를 센다. 곡선이 Qwen3처럼 나오면 동적 캐시가 다시 올라오고 행 분할의 순위가 내려간다.

## 흔들리는 전제 — 우리 문서 안의 모순

`roofline.md`는 호스트 대역폭 147.7 GB/s로 호스트 항을 22.6 ms라 하고, 같은 파일의 WKS-36 절은 검증 토큰 하나의 한계 비용을 17.28 ms로 맞춘다. 한계 토큰의 전문가는 약 98%가 새것이므로 17.28 ms는 토큰 하나의 라우팅 읽기(호스트 3.336 GB + GPU 0.708 GB) 값인데, 147.7이면 호스트 몫만으로 22.6 ms다. 두 실행은 같은 파일·같은 배치(전문가 7층 GPU, 33층 호스트)다 — 리드 확인. 기울기를 뒤집으면 β_g가 무엇이든 β_h는 200 GB/s 위다. DDR4-3600 8채널의 물리 상한이 230.4 GB/s이므로 조사의 "단일 233 GB/s 적합"은 물리가 아니라 숫자 맞춤이고, 정직한 범위는 200~230(WKS-35의 215.6 가지), 그러면 β_g도 247보다 커야 한다.

기울기가 속일 수 있는 길이 둘 남는다: 검증 배치에서 호스트가 더 빨리 읽는 경우(전문가 6개보다 12~24개가 32스레드·8채널을 더 잘 채운다), 그리고 ik가 배치 경로에서 무언가를 겹치는 경우. 어느 쪽이든 147.7은 "배치 1에서 6개 전문가를 읽는 실효값"일 수는 있어도 기계의 값은 아니다. ~~**WKS-35와 GPU 스트림 읽기 측정이 닫기 전에는 위 표의 배수를 계획 숫자로 쓰지 않는다.**~~ 2026-09-24 닫힘(E2·E4): 커널 없는 순수 읽기 140–145, 엔진 132–137, STREAM 147.7 GB/s — 기계 값은 147.7 쪽이고 215.6은 L3 잔류였다(rig-log 09-24#host-bridge-gap-is-not-the-mapping). β_h가 215 쪽이면 호스트 항이 15.5 ms로 줄고 단일 스트림 이득도 같이 준다(조사 추정 1.06~1.09배, 공유 전문가 보정 전).

## 출력이 바뀌는 쪽

Expert Deferral(일부 전문가의 출력을 다음 층에 합류)은 사슬을 끊어 1.8배 쪽 상한을 여는 유일한 길이고 KTransformers가 평균 정확도 하락 0.5% 이하를 보고한다. 우리는 공유 전문가 몫이 더 작아 이득도 더 작을 것이다. 출력 불변 레버를 다 쓴 뒤의 일이고, 우리 평가로 게이트한다.

## 순서

1. 라우터 id 덤프 실험 — 동적 캐시 대 행 분할의 우선순위를 정한다. 엔진 작업 없음.
2. WKS-35(β_h)와 GPU 스트림 읽기(β_g) — 모든 배수의 눈금.
3. B2: 그래프 안 경계 → 공유 전문가 겹침 → 행 분할 스윕. B2 게이트의 참조는 V4.1 기준 0.684 ms/층이다(0.20 ms는 Qwen3.6).
4. 독립 시퀀스 둘 이상의 처리량은 별개 행이다: 그쪽 최적 배치는 전문가를 전부 호스트에 두는 것(1.82배, 유도)이라 지연 최적과 **다른 배치**다.
