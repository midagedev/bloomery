# cuda-oxide PR — 메인테이너가 커밋을 더하지 않아도 되는 모양

우리 PR 두 개(#1314, #1321)는 둘 다 메인테이너(nihalpasham)가 커밋을 하나 더 얹고 머지했다. 이 문서는 그 커밋이 무엇이었는지, 다른 기여자의 PR에서도 같은지, 우리가 처음부터 무엇을 넣으면 그 커밋이 필요 없는지를 적는다. 표본은 2026-09-27에 읽었다.

## 1. 표본 — 누구에게나 일어난다

메인테이너 본인 PR을 뺀 최근 머지 PR 47개(#1214 – #1327)의 커밋 작성자를 셌다.

- **37개(79 %)에 메인테이너 커밋이 있다.** 커밋 56개의 종류는 코드 수정 29, 테스트 14, main 병합 7, 문서 6이다(커밋 제목 접두어로 분류).
- 커밋이 없는 10개는 작다(추가 줄 중앙값 112, 있는 쪽은 304). 기존 의미를 옮기는 리팩터(#1324), 테스트만(#1297), 의존성(#1247), 한 파일 수정(#1326, #1260)이 그렇다. 이 PR들도 리뷰에 "rebased and signed"가 적혀 있다 — 리베이스와 서명은 커밋 수에 안 잡힐 뿐 거의 항상 메인테이너가 한다.

그래서 **추가 커밋 0은 목표로 삼을 수 없다.** 이것은 이 메인테이너의 착륙 절차다: PR을 넘겨받아 검증을 자기 손으로 한 번 더 하고, 그 검증이 찾은 것을 커밋으로 남긴다. 우리가 줄일 수 있는 것은 **그 검증이 찾는 것**이다. 목표는 그의 코드 품질이다: 우리 코드와 테스트를 그가 고치거나 보탤 것이 없는 상태. 리베이스·서명·커밋 재작성은 그가 해도 된다(사용자 2026-09-27: "커밋 다시 만들어도 돼, 그 사람의 코드 품질에 맞추고 싶은 거야").

## 2. 메인테이너가 더한 것

우리 두 PR과 표본의 리뷰 본문에서 되풀이되는 것은 다섯 가지다.

1. **정수형 전체에 걸친 의미 테스트.** #1321에 더한 `partial_offset_guard_admits_exactly_the_non_wrapping_in_bounds_groups`는 i8·u8의 `min..=max` 전부와 (step, factor) 세 쌍에 대해, 생성된 가드 IR을 그 정수형의 wrapping 규칙으로 **평가**해서 "넘치지 않고 범위 안인 그룹만 들어간다"를 확인한다. #1314에 더한 것은 128비트 값, 음수 시프트 양, 64비트 위 비트가 있는 시프트 양, 결과 타입의 정확한 일치다. 우리 테스트는 몇 개의 대표 사례에서 IR의 **모양**을 봤고, 메인테이너는 경계 전체에서 IR의 **값**을 봤다.
2. **실패 경로.** 표본의 코드 수정 커밋 대부분이 이 부류다: "return an error if shifting an index overflows"(#1322), "reject failed debug policy queries"(#1253), "keep probing after unusable clang resource query"(#1307), 토큰 경계(#1322, #1260). 고친 자리의 이웃 입력 — 넘침, 잘못된 형식, 실패한 조회 — 이 이름 붙은 오류로 끝나는지를 본다.
3. **계약 문서의 정밀화.** #1321의 커밋이 고친 소스 두 줄은 문서다: `trip_count`는 "수학적 정수 위의 횟수이고, 소비자가 실제 정수형에서 넘치지 않음을 증명해야 한다". 우리 패치가 새로 기대는 가정을 공개 필드의 문서에 적은 것이다.
4. **기존 GPU 예제 안의 회귀.** #1314에 `unroll_smoke`의 새 `#[kernel]` 하나(세 버퍼, 기대값을 메시지와 함께 정확히 단언). 리뷰 본문은 매번 compute-sanitizer memcheck·synccheck 0과 LLVM·libNVVM 두 경로를 적는다.
5. **변이 논증.** "the added tests catch a truncated-count bug that the original cases miss; both regressions fail with the old folder". 테스트가 고친 코드를 일부러 망친 변형에서 실패한다는 것을 보인다.

그리고 모든 PR에 **리베이스와 서명**. 우리 커밋 `f5c44631`은 GitHub에서 `unsigned`이고, `5bc8795d`는 메인테이너가 다시 커밋해 `verified`가 됐다. CONTRIBUTING이 요구하는 것은 DCO(`Signed-off-by`)뿐이지만, 메인테이너는 서명된 커밋으로 머지한다.

## 3. 처음부터 넣을 것

PR을 열기 전에 패치가 아래를 모두 갖췄는지 본다. 각 항목은 위 2절의 번호에 대응한다.

- **(1) 경계 전체의 의미 테스트.** 고친 로직이 정수를 다루면 i8·u8(가능하면 i16·u16까지)의 전 범위를 도는 테스트 하나를 둔다 — 생성된 IR이나 결과를 그 정수형의 규칙으로 평가해 참조 계산과 비교한다. 부호 있는·없는 형, 최댓값·최솟값 근처, 빈 범위, 역순, 128비트를 명시적으로 덮는다. 테스트 이름은 문장으로 쓴다(`…_admits_exactly_the_…`).
- **(2) 이웃 입력의 실패 경로.** 패치가 인식하지 않는 형태(다른 반복자, 상수가 아닌 경계, 넘치는 식)가 이름 붙은 경고나 오류로 끝나고 그 경로마다 테스트가 있다. 조용히 건너뛰는 경로가 하나도 없다.
- **(3) 새 가정의 문서화.** 패치가 기대는 불변식(넘치지 않음, 순서, 소유)을 그것을 들고 있는 공개 타입·필드·함수의 `///`에 한 문장으로 적는다.
- **(4) GPU 회귀.** 기존 예제(`unroll_smoke` 등)에 `#[kernel]` 하나, 기대값 정확 단언, `SUCCESS` 표식. memcheck·synccheck 0을 확인한다. libNVVM 경로를 돌릴 수 없으면 본문에 "LLVM path only"라고 쓴다.
- **(5) 변이 확인.** 새 테스트 각각이 수정 전 소스에서 실패하고, 고친 줄을 한 줄 망친 변형에서도 실패하는지 본다. 본문에 한 줄: "the new tests fail on main and on a variant that <망친 방식>".
- **리베이스와 검사.** 열기 직전에 업스트림 main 위로 리베이스하고, `just check`(전체), `cargo oxide fmt`, 두 워크스페이스의 `clippy -D warnings`를 그 트리에서 돌린다. 커밋은 DCO를 단다.
- **범위.** 한 목적 한 PR. 테스트를 빼고 본체가 수백 줄이면, 먼저 이슈(또는 닫힌 이슈 인용)로 방향을 확인한다. CONTRIBUTING의 절차 1이 "이슈 먼저"다.

본문은 메인테이너가 쓰는 검증 문장 모양을 짧게 따른다(`just check` 테스트 수, FAIL-first, GPU·memcheck·카드). 길이는 사용자 규칙대로 템플릿 빼고 100단어 안이다.

## 4. 지금 적용 — 원장 31(범위 `for` 언롤)

oxfix2의 패치(`canonicalize.rs`의 `thread_iterator_exit_test`, 약 1,000줄 중 테스트 약 400줄)를 열기 전에 3절로 대조할 항목:

- (1) `for i in a..b`의 반복 횟수를 i8·u8 전 범위의 (a, b) 쌍과 여러 언롤 배수에서 평가하는 테스트: 빈 범위(a ≥ b), a = b − 1, b = MAX, 부호 있는 범위가 0을 가로지르는 경우.
- (2) 인식하지 않는 반복자(`a..=b`, `.step_by`, `.rev()`, 상수가 아닌 경계, 본문 안 `break`)마다 경고 문구와 그 테스트.
- (3) `thread_iterator_exit_test`가 기대는 MIR 모양(`Range::next` 인라인, `Option` 판별 검사)을 그 함수의 `///`에.
- (4) `unroll_smoke`의 새 커널에 memcheck·synccheck 결과.
- (5) 변이 한 줄과 그 실패.
- #559(닫힘)를 인용하고, 그 이슈가 요구한 동기를 우리 숫자로 한 문장.

## 5. 코드 품질 기준 — 그가 쓰는 방식

2절은 그가 **무엇을 더했나**이고, 이 절은 그가 **어떻게 쓰는가**다. 라운드 `oxstyle`(09-27)이 그가 외부 PR 32개에 얹은 커밋 47개, 리뷰 81개, 그의 PR과 `mir-transforms` 기존 코드를 읽고 뽑았다. 근거가 세 곳 이상인 것만 적는다.

**테스트**
- 새 테스트는 고치기 전 코드에서 실패해야 하고, 리뷰 본문에 그렇게 쓴다. 양성 사례마다 대조군(바뀌지 않아야 하는 사례)을 하나 둔다.
- 값은 타입 경계에서 고른다(`[-128, -127, -1, 0, 1, 126, 127]`, 128비트, `1<<64`). 도메인이 작으면(i8·u8, 런치 모양 77개) 전부 돈다.
- 판정은 독립 오라클로 한다: 생성된 IR을 정수형 규칙으로 평가하는 `evaluate_integer`처럼. IR 모양 단언은 정확할 때만 쓰고 값을 단언한다. 테스트 IR은 verifier를 통과시킨 뒤에 단언한다.
- 계약 하나에 테스트 하나, 사례는 `for … in [..]` 표로 두고 assert 메시지에 사례 튜플을 넣는다. 테스트 이름은 문장형 snake_case이고 테스트에 `///`를 달지 않는다(62개 중 61개) — 무엇을 잡는지는 본문 주석 한 줄.
- 헬퍼는 파일 안에 짧게 둔다(`evaluate_integer` 45줄). 기존 빌더를 재사용하거나 그 자리에서 넓히고, 헬퍼 모듈을 새로 만들지 않는다.
- 코드젠 수정에는 기존 GPU 예제에 커널 하나(버퍼 몇 개, `assert_eq!` + 메시지)를 붙이고, 리뷰에 memcheck·synccheck과 LLVM·libNVVM 경로를 적는다.
- 경고 문자열은 테스트하지 않고 구조만 본다. 에러 문자열은 테스트한다.

**코드**
- 인식하지 못하면 이름 붙은 건너뜀이나 에러로 끝낸다(fail-closed). 분석의 미인식은 `Option`, 입력 거부는 `Result<_, String>`, 불변식은 `expect("<불변식>")`.
- 메시지는 소문자, 대상을 백틱으로, 그다음 규칙("unsupported … `{name}`; only … is supported"). 언롤 경고는 `{kind} requested but the loop was not unrolled: {reason}` 형식이고 함수 이름을 넣지 않는다.
- 정수는 i128에서 checked로 계산하고 좁히기 전에 범위를 본다. wrapping은 테스트 모델에서만 쓴다. 넘치지 않음을 누가 증명하는지 문서에 적는다.
- 공개 표면은 최소(`unroll.rs` 함수 30개 중 pub 1개). 함수는 길이 때문이 아니라 결정을 테스트할 수 있게 쪼갠다. 한 사실에 구현 하나 — 두 번째 파서나 평가기를 만들지 않는다.

**문서와 주석**
- 모든 함수에 반환, `None` 조건, 호출자 의무를 적은 1–4줄 doc. 본문 주석은 적고(최근 패치의 주석/코드 비율 중앙값 0.03), 있으면 이유다. 기여자의 긴 산문은 계약 문장으로 줄이고 이력(`(#1292)` 같은 것)을 지운다. ASCII 도식은 모듈 doc과 픽스처에만.
- 커밋 메시지는 `type(scope): lowercase imperative`, 본문은 거의 없고 설명은 리뷰 본문으로 간다.

**적용 결과(#1346).** 이 기준으로 다시 본 결과, 올린 판에 실결함이 하나 있었다: 루프를 가로질러 살아 있는 스칼라가 있으면 매치 체인에 블록 인자가 생겨 언롤이 경고와 함께 빠졌다(PR의 커널들은 루프가 하나씩이라 드러나지 않았고, 스모크 커널을 그의 형식대로 하나로 합치자 나왔다). 고치고, 190줄짜리 새 인터프리터를 그의 `evaluate_integer` 재사용으로, 테스트 `///` 열 개를 본문 주석으로, 건너뜀 테스트 넷을 표 하나로, 스모크 커널 다섯을 하나로 바꿨다. 추가 줄은 1,599 → 1,177, 테스트 바이너리 24.5 → 5.2 s, `just check` 5,506 통과, libNVVM 경로까지 memcheck·synccheck 0.
