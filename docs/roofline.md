# 디코드 루프라인 — 토큰 하나에 몇 바이트를 읽는가

날짜 2026-09-19. **이 문서의 바이트 수는 GGUF 헤더를 직접 파싱해 잰 것이고, tok/s는 거기서
도출한 값이다.** 대역폭은 실측치를 쓰되 출처를 행마다 적는다. 도출은 도출이라고 밝힌다.

왜 이걸 먼저 쓰는가: 디코드가 대역폭 바운드라면 커널을 아무리 잘 써도 천장이 있고, 그 천장은
바이트 수가 정한다. 어떤 기법을 검토하든 "루프라인의 어느 항을 얼마나 줄이는가"로 환원되지
않으면 그것은 설계 입력이 아니다.

## 모델이 토큰 하나에 읽는 바이트

MoE 디코드에서 라우팅되지 않은 expert는 읽지 않는다. 그래서 파일 크기가 아니라 **활성 바이트**가
분모다.

| | DeepSeek-V2-Lite-Chat Q3_K_M | DeepSeek-V4.1-Flash Q3_K_M-engramQ8 |
|---|---:|---:|
| 파일 전체 | 7.565 GiB | 444.23 GiB |
| 블록 수 | 27 (dense 1 + MoE 26) | 40 |
| expert | 64개 중 6개 | 384개 중 6개 |
| 라우팅 expert / 토큰 | 0.6481 GiB | 3.7656 GiB |
| dense(어텐션·shared·헤드·라우터) / 토큰 | 0.5690 GiB | 7.1320 GiB |
| engram 테이블 | 없음 | 194.867 GiB 중 **토큰당 5.2 KiB** (rig-log 2026-09-16) |
| **토큰당 합계** | **1.2171 GiB = 1.307 GB** | **10.8976 GiB = 11.701 GB** |
| 활성 비율 | 16.1 % | 2.45 % |

V2-Lite의 expert 하나(gate+up+down)는 4.254 MiB다: gate·up이 Q3_K 2048×1408, down이
**Q5_0** 1408×2048. V4.1은 블록당 라우팅 expert 바이트가 0.1011 GB/토큰이다.

## 천장

### V2-Lite — 3090에 통째로 들어간다

| 대역폭 근거 | GB/s | 천장 |
|---|---:|---:|
| 우리 q3k gemv 실측 (0단계, stack M=1) | 348 | 266 tok/s |
| ggml `mmvq` 실측 (같은 자리) | 333 | 255 tok/s |
| 3090 스트림, 이론 936의 81 %로 **도출** | 760 | 582 tok/s |
| 호스트 32스레드 실측(잠정) | 147.7 | 113 tok/s |
| 호스트, 4라운드 실측 | 215.6 | 165 tok/s |

디딤돌은 대역폭에 굶지 않는다. 1단계의 게이트는 정확도이고 속도는 1-5에서 처음 의미가 생긴다.

### V4.1 — 여기서 루프라인이 문다

서빙 배치(rig-log 2026-09-16)는 라우팅 expert를 A6000 4⅓ 블록, 3090 2⅔ 블록, **DDR4 33 블록**에
둔다. 어텐션·shared·헤드·라우터는 전부 GPU다.

| 항 | 바이트/토큰 | 어디 |
|---|---:|---|
| 라우팅 expert, 호스트 33 블록 | 3.336 GB | DDR4 |
| 라우팅 expert, GPU 7 블록 | 0.708 GB | VRAM |
| dense 전부 | 7.658 GB | VRAM |

| 가정 | ms/토큰 | tok/s | 호스트 항 | GPU 항 |
|---|---:|---:|---:|---:|
| 호스트 147.7 + GPU 500 | 39.3 | 25.4 | 22.6 ms | 16.7 ms |
| 호스트 147.7 + GPU 700 | 34.5 | 29.0 | 22.6 ms | 12.0 ms |
| 호스트 215.6 + GPU 500 | 32.2 | 31.1 | 15.5 ms | 16.7 ms |
| 호스트 215.6 + GPU 700 | 27.4 | 36.5 | 15.5 ms | 12.0 ms |
| **ik 실측 (2026-09-16)** | **39.92** | **25.05** | | |

첫 행이 실측과 1.5 % 안에서 만난다. **그것을 증명으로 읽지 않는다** — GPU 유효 대역폭 500 GB/s는
고른 값이지 잰 값이 아니고, 자유 파라미터 둘로 한 점을 맞춘 것은 맞춤이지 확인이 아니다.
잰 것만으로 말할 수 있는 것은 이것이다:

> **호스트 33 블록의 expert 읽기 3.336 GB는 실측 147.7 GB/s에서 22.6 ms이고, 이는 실측된
> 토큰 시간 39.92 ms의 57 %다.**

이 한 줄이 설계를 정한다. 토큰당 바이트를 줄이거나 한 번 읽은 바이트를 여러 토큰에 나눠 쓰지
않는 기법은, 그것이 무엇이든 큰 폭의 이득을 낼 수 없다.

## 여기서 갈라지는 질문들

- 호스트 대역폭이 147.7인가 215.6인가. 4라운드에서 두 엔진이 317 MB 작업 집합으로 147.7을
  넘었다(L3 잔류 의심). 215.6이 맞으면 호스트 항은 15.5 ms이고 남은 24 ms의 설명이 따로
  필요해진다 — 그때는 병목이 대역폭이 아니다. **rig-log WKS-35의 판별 실험이 이 갈림길을 닫는다.**
- GPU 유효 대역폭을 재지 않았다. 조용한 기계에서 A6000·3090 각각의 스트림 읽기를 한 번 재면
  위 표의 자유 파라미터가 하나 줄어든다.
- KV는 이 계산에 없다. V4.1은 MLA(kv_lora 512 + rope 64)에 인덱서 top_k 512라 컨텍스트가
  1 M이어도 층당 읽는 KV는 512 엔트리다 — 40층 × 512 × 576 × 2 B ≈ 23.6 MB, 가중치 11.7 GB
  옆에서 0.2 %다. DSA가 이미 이 항을 닫았다.

## 기계 균형점 — 이 박스는 M=1에서 자기 능력의 1/5로 돈다

위 표는 "바이트를 얼마나 빨리 읽는가"만 본다. 반대쪽을 같이 봐야 어디가 노는지 보인다.
아래 FLOPS는 **도출값**이다: 클럭은 박스에서 읽은 base 3.6 GHz(`scaling_max_freq` 3600000),
Zen 3의 256비트 FMA 유닛 2개, AVX2 8레인, FMA는 2 flop으로 센다. int8은 `vpmaddubsw`+`vpmaddwd`
사슬이 코어·사이클당 int8 MAC 32개를 지속한다고 보수적으로 잡았다 — **재지 않았다.**

| | f32 | int8 |
|---|---:|---:|
| 호스트 32코어 (도출) | 3.69 TFLOP/s | ~7.4 TOPS |
| 호스트 균형점 @ 147.7 GB/s | **24.9 flop/byte** | **49.9 op/byte** |
| 호스트 균형점 @ 215.6 GB/s | 17.1 | 34.2 |
| 3090 (사양) | 35.6 TFLOP/s | 142 TOPS (dense) |
| 3090 균형점 @ 760 GB/s (도출) | 46.8 | 187 |

Q3_K gemv가 바이트당 요구하는 것은 얼마인가. 슈퍼블록 110바이트가 가중치 256개를 담고,
가중치 하나당 곱 하나 합 하나다. **512 flop / 110 byte = 4.65 flop/byte.**

토큰 k개를 같은 가중치 패스로 처리하면 이 값은 4.65k가 된다. 균형점에 닿는 k는:

| | k (f32) | k (int8) |
|---|---:|---:|
| 호스트 @ 147.7 GB/s | **5.4** | 10.7 |
| 호스트 @ 215.6 GB/s | 3.7 | 7.3 |
| 3090 @ 760 GB/s | 10.1 | 40.2 |

읽는 법: **호스트는 토큰 5개까지는 계산을 공짜로 더 할 수 있다.** 지금 M=1로 도는 동안
호스트의 산술 유닛은 자기 균형점의 19 %에서 논다. GPU는 int8 기준 2.5 %다. 이 박스는
대역폭이 모자란 기계가 아니라 **가중치 바이트 하나를 2 flop에만 쓰고 버리는 기계**다.

### 그래서 호스트를 "느린 GPU"로 보는 틀이 틀렸다

지금의 배치는 방어적이다 — expert가 VRAM에 안 들어가니 남는 것을 DDR4에 둔다. 호스트는
GPU가 하던 일을 더 느리게 한다. 숫자는 다른 말을 한다: 호스트가 부족한 것은 대역폭이고
남는 것은 계산이다. 그러면 호스트에 줘야 할 일은 **바이트당 계산이 많은 일**이다.

- **투기 디코딩의 검증이 정확히 그 모양이다.** 드래프트 토큰 k개를 같은 expert 가중치로
  검증하면 바이트는 그대로고 계산만 k배다. 호스트에서 k=5까지는 시간이 늘지 않는다.
- **호스트와 GPU는 지금 직렬이다.** 위 표에서 22.6 ms + 16.7 ms를 더해 실측과 만난 것이
  그 증거다. 한 토큰 안에서 층 N은 N+1보다 먼저 끝나야 하니 겹칠 수가 없다. **토큰이 둘
  이상 떠 있으면** 둘은 파이프라인 두 단이 되고 39.3 ms가 max(22.6, 16.7) = 22.6 ms가 된다.
  **커널을 한 줄도 안 고치고 1.74배다.** 스케줄러만의 몫이고, 엔진을 직접 쓰는 이유이기도 하다.
- 이 둘은 같은 전제를 요구한다: **토큰이 여러 개 떠 있는 순전파.** 그래서 `[embd, n_tokens]`
  결정(`docs/plan.md`)이 두 번 짊어진다.

### 256 GB는 무엇에 쓰는가

가중치 저장은 이미 그 용도다. 남는 질문은 **바이트를 재사용하는 데 RAM을 쓰는 길**이다.
engram 194.9 GiB는 NVMe에서 토큰당 5.2 KiB만 읽으므로 상주시켜도 처리량은 안 바뀐다(지연만).
실제로 아픈 곳은 따로 있다 — 13k 프리픽스가 편집 한 번에 통째로 재프리필된다(rig-log,
2026-09-17). 이건 루프라인 밖의 워크로드 차원 비용이고, 256 GB면 대화 상태를 아주 많이
들고 있을 수 있다. 어느 쪽이 큰지는 재야 안다.

**이 절의 숫자는 전부 도출이다.** 호스트 FLOPS도 int8 처리율도 3090 유효 대역폭도 재지 않았다.
판단을 걸기 전에 재야 하는 것: ① 코어 32개 AVX2 FMA 지속 처리율 ② `vpmaddubsw` 사슬의 실제
int8 op/s ③ A6000·3090 스트림 읽기 ④ 호스트 대역폭 147.7 대 215.6.
