# 게이트 시간 계획 — 3분이던 것이 36분이 된 이유와 되돌리는 순서

사용자 질문(2026-09-25 밤): "예전에는 게이트 돌리는 데 3분도 안 걸렸는데 왜 지금은 이렇게 오래 걸리나. 전체 경로를 타는
엔드투엔드 두어 개만 스모크로 돌리면 되지 않나." 이 문서는 그 답과 계획이다. 규칙은 그대로다: **게이트를 완화하지
않는다**, 뺀 게이트는 사유를 적은 기록이지 판단이 아니다(`AGENTS.md` 「Never」, `just affected`의 머리말).

## 1. 지금 얼마나 걸리고 어디에 쓰이나 (2026-09-25 실측)

리드 착륙 묶음 둘, 레시피를 직렬로 한 차선(3090 게이트 락)에서 돌린 값이다. 라운드가 이미 같은 게이트를 녹색으로
돌린 뒤 리드가 자기 소유로 다시 돈 것이다.

| 묶음 | 레시피 수 | 합계 | 그중 GPU 게이트 |
|---|---:|---:|---:|
| fixup5(`7928a0f`) | 48 | 2,167 s (36분) | 29개 1,986 s |
| ds41bulk(진행 중) | 38 | 첫 26개 1,772 s | — |

큰 것부터(fixup5 묶음, 레시피 하나의 벽시계 = rsync + 빌드 확인 + 락 + 실행):

| 레시피 | s | 왜 큰가 |
|---|---:|---|
| `gate-gpu-ds41-prefill` | 386 | 케이스 12개(P = 1…4096), P = 4096 케이스가 절반 이상; ds41bulk 묶음은 두 팔이라 ×2 |
| `gate-gpu-p4` | 229 | V2-Lite 커널 케이스 다수 |
| `gate-gpu-ds41-draft` | 164 | 초안 헤드 + 스텝 쌍 |
| `gate-gpu-e2e` | 150 | V2-Lite 전 경로, MMA 두 팔 |
| `gate-gpu-gemm` | 134 | Qwen3 GEMM 케이스 |
| `gate-ptx-spill` | 59–127 | 두 바이너리 빌드 + ptxas |
| `gate-gpu-qwen3moe-e2e` | 126 | Qwen3 전 경로 |
| dspark-loop · long · serve · engram · moe | 65–106 | 각각 모델을 열고 케이스 몇 개 |
| 30 s 미만 32개 | 1,154 | **거의 전부 적재 비용**: V4.1 게이트는 하나마다 카드 23 GB + 호스트 집합을 다시 연다(`load … in 30.0 s`) |

분해하면 셋이다.

1. **개수.** 3분이던 때(2026-09-20)는 V2-Lite 16 GB의 CPU 서브시스템 게이트 13개였다. 지금은 레시피 92개(V4.1 25,
   Qwen3 10, V2-Lite 15, DSpark 5, CPU 11, 정적 8, …)이고 착륙 묶음이 38–49개다.
2. **게이트당 고정비.** V4.1 GPU 게이트 25개가 각자 모델을 연다: 적재 30 s × 25 ≈ **12.5분**이 케이스와 무관한 비용이다.
3. **직렬 한 차선.** 카드마다 게이트 락이 따로 있는데(`/root/bloomery-gate.lock`, `-a6000.lock`) 묶음은 3090 한 줄로
   합산된다. 다른 트랙과 겹치면 rc 75 재시도까지 붙는다.

## 2. 목표

| 층 | 언제 | 목표 벽시계 | 무엇을 잡나 |
|---|---|---:|---|
| **스모크** | 라운드 중·리베이스 뒤·리드 첫 판정, 항상 | **≤ 8분** | 전 경로 비트(디코드 = 프리필 = 스텝), V2-Lite 전 경로, 정적 |

## 3. 순서 — 각 단의 유도와 크기

### 3.1 스모크 층 `just smoke` (S, 러너 + 레시피)

전체 경로를 타는 게이트 셋 + 정적 검사. 오늘 라운드들의 빨강(ee의 `Fault` 리터럴, 폴트 마스크, 라우터 프로브, 그룹
커널의 이웃 슬롯)이 전부 이 셋 안에서 잡혔을 것이다.

| 구성 | s [유도, 오늘 실측에서] | 근거 |
|---|---:|---|
| 정적: check-recipes·check-rustflags·check-comments·check-arch·check·fmt-check·lint | ≈ 40 | 오늘 5–17 s씩 |
| `gate-gpu-ds41-step` | 43 | 디코드 스텝 비트 + 폴트 |
| `gate-gpu-ds41-prefill` **P = 512 케이스만** | ≈ 60–90 | 프리필 = 스텝 비트; 지금 386 s는 12 케이스 합, P = 1100이 11 s |
| `gate-gpu-e2e` | 150 | V2-Lite 전 경로, 폴트 워드의 argmax 복사 |
| **합** | **≈ 5–6분** | 한 차선 직렬 |

필요한 변경: prefill 게이트에 케이스 선택 인자(`--cases 512`처럼 이름으로; 없는 케이스는 거부), `just smoke` 레시피,
`check-recipes`가 스모크 레시피가 세 게이트를 실제로 부르는지 확인. 스모크는 **전체를 대신하지 않는다** — 라운드
중 반복과 리드의 첫 판정용이고, 착륙은 전체 층이다.

### 3.2 전체 층의 목록 = `just affected` (착륙 `1ea27fa`, 이미 있음)

묶음은 손으로 고르지 않고 이 목록에서 시작한다. 뺀 것은 변경 클래스 표(`AGENTS.md` 「Derive first」)로 사유를 적는다 —
오늘 ds41bulk 묶음이 그 첫 사례(59 중 38, 뺀 30의 사유 = 기존 PTX 엔트리 digest 동일). 실측: v4meta 21/84, fixup5
48/76, ds41ced 21/59 — 리드가 빠뜨린 것 14개가 있었다(`gpu-deepseek41`을 링크하는 게이트).

### 3.3 두 차선 러너 (XS–S, `tools/gate-batch.sh`)

카드별 락이 둘이므로 목록을 두 차선으로 나눠 병렬로 돈다. V4.1 `--place gate` 게이트는 3090 전용이고, 나머지(`any`
카드 레시피: qwen3moe·gemm·e2e·p6·chain-ffn·vision·dspark-kv)는 A6000으로 보낸다.

[유도] fixup5 묶음이라면 3090 차선 ≈ V4.1 25개 1,300 s, A6000 차선 ≈ 나머지 GPU 12개 + CPU 11개 ≈ 900 s → 벽시계
≈ 1,300 s(22분), 36분에서 −40 %. 러너는 레시피 목록·차선 배정·rc 75 재시도·레시피별 로그 파일·`DONE` 센티널을
갖고, 타이밍 임대가 잡혀 있으면(`flock -n`) 시작하지 않는다(시팅 오염 방지). 오늘 리드가 손으로 쓴 `gates.sh` 셋이
그 원형이다.

### 3.4 원장 층 `just gates-affected` (M, `spec-gatesaffected.md` 2층)

입력 내용 해시(타깃의 소스 닫힘 + 스크립트 + 레시피 텍스트 + 툴체인 핀 + 카드)를 키로, 러너가 **rc 0일 때만** 쓰는
원장 `/root/bloomery-gate-ledger.tsv`. 해시가 같은 게이트는 `skip <recipe> (green at <commit>)`로 찍고 건너뛴다.
효과가 큰 곳은 리베이스 뒤 재실행이다: 오늘 fixup5는 리베이스 뒤 14개를 다시 돌렸는데(ee의 q3ubatch 델타), 입력이
안 바뀐 것은 원장이 건너뛴다. 라운드의 게이트 실행은 원장에 쓰지 않는다(리드 묶음만, `BLOOMERY_GATE_LEDGER=1`).

### 3.5 적재 공유 — V4.1 게이트를 한 번 연 모델 위에 (M)

25개 게이트 바이너리가 각자 `body::open`을 부른다. `gate_e2e`처럼 **한 바이너리의 서브커맨드(팔)** 로 접어 모델을 한
번 열고 케이스를 이어 돌리면 적재 25회 → 3회(V4.1 gate 배치 · DSpark · Qwen3). [유도] −12분 이상. 조건: 케이스
사이에 `reset`과 `take_fault`로 상태를 지우고, 케이스가 독립임을 게이트가 스스로 확인(순서를 바꿔 한 번 돌려 같은
판정). 바이너리 수가 줄면 `ptx-spill`·`affected`의 표도 줄어든다. 이건 게이트 저작 구조의 변경이라 한 라운드가
V4.1 게이트 25개를 모두 읽어야 하므로 3.1–3.4 뒤에 연다.

### 3.6 prefill 게이트 케이스 재배치 (XS, 3.1과 함께)

12 케이스 중 P = 4096·2600·1100은 CED 삼각형·창 케이스이고 P = 1…513은 경계 케이스다. 스모크는 512 하나, 전체는
전부. 두 팔(expert·slot)은 전체 층에서만.

| 단계 | 스모크 | 전체(fixup5 크기 기준) |

## 5. 하지 않는 것

- 게이트를 지우거나 케이스를 줄여 통과시키는 것. 케이스 선택은 스모크의 **부분집합 실행**이고 전체 층은 전부 돈다.
- 라운드의 녹색을 리드의 녹색으로 치는 것. 원장은 리드 러너만 쓴다.
- 타이밍 시팅과 게이트 묶음을 겹치는 것(빌드 CPU 부하가 시팅을 오염시킨다) — 러너가 임대를 본다.

## 6. 순서와 주인

1. `smoke`(3.1 + 3.6) — 다음 대기 창의 S 라운드(러너·레시피·prefill 케이스 인자). 리드가 스펙.
2. 두 차선 러너(3.3) — 같은 라운드에 넣거나 바로 뒤 XS.
3. 원장(3.4) — `spec-gatesaffected.md` 2층, M.
4. 적재 공유(3.5) — M, V4.1 게이트 독해가 필요해 조용한 창에.

측정 규율: 각 단은 착륙 뒤 같은 묶음(fixup5 크기의 목록)을 한 번 돌려 이 표의 예측과 실측을 나란히 적는다.
